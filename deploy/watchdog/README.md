# 外部看门狗（Uptime Kuma）

> 规格 §9.4「告警渠道」·宪法 23 条「外部看门狗必须独立故障域和独立通知链」
> ·XM-0033

平台内部的告警中心（`internal/platform/alerts`）负责回答「上游数据对不对、
渠道余额够不够」。它答不了一个问题：**平台自己挂了怎么办。**

那是这个栈的职责，也是它必须活在平台外面的原因。

---

## 两条红线

这两条不是建议，是规格 §9.4 与宪法 23 条的明文要求。违反其中任何一条，
这个栈就退化成一个装饰品——它会在平台正常时安静地绿着，在平台真出事时
一起沉默。

### 红线一：必须部署在**异故障域**

看门狗和被监控对象不能共享任何单点：

| 共享的东西 | 后果 |
|---|---|
| 同一台宿主 | 机器掉电 / 内核 panic → 平台和看门狗一起没了，没有人被通知 |
| 同一个 Docker daemon | daemon 崩溃或被 `systemctl restart docker` → 同上 |
| 同一个机房 / 可用区 | 断电、断网、机房级故障 → 同上 |
| 同一条上行网络 | 出口断了 → 看门狗探不到平台，也发不出通知 |
| 同一个云账号 | 账号欠费 / 被封 → 同上 |

**推荐部署位置**（按成本从低到高）：

1. 另一个云厂商的最小规格 VPS（月成本个位数美元，足够跑 Uptime Kuma）；
2. 同一云厂商的**另一个区域** + 独立付费方式；
3. 办公室 / 家里的一台常开小主机（注意它的上行网络本身是否可靠）。

**不可接受**：与 `deploy/compose/launch.yaml` 同一台机器。这就是本文件
所在的这个 compose 栈**刻意不并进** `launch.yaml` 的原因——一条
`docker compose -f launch.yaml up` 就能把两者一起拉起来的设计，
本身就是在鼓励人把它们放在同一台机器上。

### 红线二：通知链**不得经过平台**

规格 §9.4 的原话：

> 外部看门狗通知不得经过星芒平台，否则平台故障时无法通知。

具体到配置上：

- **另建一个 Telegram Bot**，不要复用 `XM_ALERT_TELEGRAM_BOT_REF` 指向的
  那一个。理由不只是「平台挂了 Bot 还在」——那个 Bot 的 token 存在平台的
  凭据体系里，平台起不来的时候你也拿不到它；
- **另建一个收件会话**（另一个群 / 另一个频道），或者至少确认现有会话里
  有人真的会看。两条链路指向同一个没人看的群，等于只有一条；
- **不要**把 Uptime Kuma 的通知配成「调用平台的 webhook」。那正是这条
  红线要禁的东西；
- 邮件通知走独立的 SMTP（或第三方通道），不要用平台所在机器上的
  邮件转发。

一个能自我验证的检查：**把平台整个停掉，看门狗必须在几分钟内把通知送到
你手机上。** 没做过这个演练的看门狗，不算数（宪法 22 条对备份的要求，
同一条道理）。

## 监控什么

平台暴露了两个不需要身份的探针（`internal/platform/httpapi/router.go`）：

| 端点 | 含义 | 建议判据 |
|---|---|---|
| `GET /healthz` | 进程活着（不查数据库） | HTTP 200；60 秒间隔；连续 2 次失败告警 |
| `GET /readyz` | 进程活着**且**数据库可达 | HTTP 200；60 秒间隔；连续 2 次失败告警 |

两个都要监控，不能只监控一个：

- 只监控 `/healthz`：数据库挂了但进程还在，探针照样 200，看门狗一片绿，
  而整个平台其实什么都读不出来；
- 只监控 `/readyz`：数据库抖一下就报警，而进程本身好好的。分不清
  「进程死了」和「数据库连不上」会让值班的人第一步就走错方向。

两者同时红 = 进程或整机的问题；只有 `/readyz` 红 = 数据库或连接的问题。

**另外建议监控**（可选，按需）：

- `GET /` 或前端入口（`web` 容器）：确认反代与静态资源这条链路也活着；
- 证书有效期：Uptime Kuma 的 HTTP 监控自带 TLS 到期提醒，
  证书过期是最容易被忘掉的那种「计划内故障」。

探针**不带身份**是有意的（见 `router.go`：`/api/v1/*` 才要 Principal），
所以看门狗不需要任何平台凭据。这也是红线二能成立的前提之一。

## 部署

### 1. 起栈

在**看门狗那台机器**上（不是平台那台）：

```bash
# 只需要这一个目录，不必检出整个仓库
docker compose -p xingmang-watchdog -f docker-compose.watchdog.yaml up -d
```

镜像已钉到 tag + digest（见 `VERSIONS.lock` 的 `uptime-kuma.*`）。
tag 会被上游重新指向，digest 不会——一个被悄悄换掉的看门狗镜像，
是所有监控里最不该出现的东西（宪法 §4）。

### 2. 首次配置

浏览器打开 `http://127.0.0.1:3001`（默认只绑回环，见下面「暴露方式」），
创建管理员账号，然后：

1. **加两个 HTTP(s) 监控**：
   - 名称 `xingmang-api-healthz`，URL `https://<平台域名>/healthz`
   - 名称 `xingmang-api-readyz`，URL `https://<平台域名>/readyz`
   - 心跳间隔 `60` 秒，重试 `2` 次，接受状态码 `200-200`
   （不要写成 `200-299`：一个 302 跳到登录页也会被算成健康）
2. **加通知渠道**：Telegram，填**独立** Bot 的 token 与 chat id（红线二）；
3. 把这个渠道**勾选到每一个监控上**——Uptime Kuma 里新建的通知渠道
   默认不会自动挂到已有监控上，这是最常见的一个「配了但不通知」的坑；
4. 用「Test」按钮真的发一条，确认手机收得到。

### 3. 验证（必须做）

```bash
# 在平台那台机器上
docker compose -p xingmang-launch -f deploy/compose/launch.yaml stop platform-api
# 等 2~3 个心跳间隔，确认手机收到通知
docker compose -p xingmang-launch -f deploy/compose/launch.yaml start platform-api
# 确认收到恢复通知
```

没跑过这一步就写「看门狗已部署」是不诚实的（宪法 1 条：可验证优先）。

## 暴露方式

compose 里默认 `WATCHDOG_BIND=127.0.0.1`：看门狗的控制台能看到平台的
内部地址、探针 URL 与全部历史状态，不该因为一个默认值就开到公网。

远程访问选一种：

- **SSH 隧道**（最简单，推荐）：
  `ssh -L 3001:127.0.0.1:3001 <看门狗主机>`，然后本地开 `http://127.0.0.1:3001`；
- **前面加一层带 TLS 与鉴权的入口**：改 `WATCHDOG_BIND=0.0.0.0`
  并在前面放 Caddy / Nginx。Uptime Kuma 自己有登录，但把它直接裸奔到公网
  意味着它的登录页成了唯一一道门。

## 谁来看着看门狗

看门狗自己也会挂，而它挂了没有第二个看门狗会发现。三道递减的保障：

1. `restart: unless-stopped` + 容器内 healthcheck：进程级故障能自愈；
2. Uptime Kuma 的 **Push 监控**（可选）：配一个「N 分钟内没收到心跳就告警」
   的被动监控，由平台侧或第三方定时器去 push——注意这条会重新引入对平台的
   依赖，只当作补充，不能替代前面两条；
3. **人**：每月一次的手动演练（停平台 → 看是否收到通知）。这一条最土，
   也是唯一真正验证了整条链路的。

## Foundation-A 边界

本档只做「探针 + 独立通知」。**不做**：

- 与平台告警中心的双向联动（看门狗的状态不回写平台，平台的告警也不发给
  看门狗）——那会重新建立一条依赖，正是红线二要禁的；
- 状态页（Status Page）对外发布；
- 多探针点（从多个地域探测同一个端点，用于区分「服务挂了」与
  「我这条网络到不了」）。

后两项属于 Foundation-B 的运维成熟度，不在 XM-0033 范围内。
