## 三、读者之间不一致、或明确拿不准的地方

**1（最重要）：「模拟数据 fake」这件事，我们四个人一致判断日志在说假话，但谁也没法确认。**
worker 的环境变量写着 `XM_NEWAPI_MODE=fake` / `XM_SUB2API_MODE=fake`，日志也打 `newapi_mode=fake`。但：

- 08-30 之后，环境变量只是**兜底默认值**，真正生效的模式每轮从数据库表 `core.connector_config` 读；上线检查单原文就写着「这里只是兜底」。
- 如果真在跑假数据，要么六条指标全成功（假客户端不会失败），要么六条**全部**失败并标「不支持」（生产环境禁止跑假数据）。实际是六条里**恰好三条**失败、错误码是「读不到」，两种假数据形态都对不上。
- 更硬的一条：sub2api 探到了 0.2.2 → 0.2.3 的**真实**版本变化，而假客户端的版本是写死的 0.1.152、永远不会变。

结论：实际跑的极可能是真实对接。但这是**推断**，我们只读、不连库。**需要你核实一眼**：后台「设置 → 凭据 → 接入模式」里 sub2api / newapi 生产那两行写的是什么。顺带三处必须知道的：日志里那个模式字段打的是环境变量而不是本轮真正生效的模式；两份「切换到真实对接」的操作手册还在教人看这个字段来验证，照着做会得出「没生效」的错误结论；还有一处后台接口在读不到数据库行时一律回答「fake」、根本不看环境变量，与实际行为方向相反。**同一个问题，系统里有三个互不一致的答案，没有一个问的是真正做决定的那段代码。**

**2：NewAPI 那三条失败，有两个都自洽的解释。** (a) 20 秒读取预算被前两组用光，后三组顺次被判超时——这个能一字不差地解释「为什么恰好是排在后面的那三条」；(b) 那三个上游接口各自出了故障。区分办法是看日志里每次读取的耗时（预算说会看到第 3 次接近 20 秒、后两次几乎零耗时返回；接口故障说则三次都有实际往返）。我倾向 (a)，但没有生产的逐次耗时数据。

**3：「CPA 指标 24 小时内 0 条」这句话有两种读法。** 如果指连「我尝试过了」的记录都没写，那是平台这边的采集任务根本没在跑；如果只是在复述「最新数据时刻停在 09-06 13:53」，那采集在跑、坏的是服务器上的快照发布。两种都要去服务器上查，但要查的东西不同。只读查不出来。

**4：card_sync 到底为什么被拒绝，没人答得出来。** 这不是能力问题——**这条信息在系统里根本没被保存下来**。仓库里也没有卡片接口的错误码表（官方文档里那些端点只定义了成功响应）。几个未验证的猜测，按可能性排：批次里混进了上游不认的卡号（比如正在删除中的卡）；这个接口的成功码可能不是 0（那样一次完全正常的响应也会被判成「拒绝」）；接口的真实形态与文档不一致（上限、去重、字段等）。**在把上游的原话取出来之前，任何根因判断都是猜。**

**5：一处读者间的分歧，已核对。** 关于 Sub2API 那格，一位读者说那条余额指标「从来没有观测」，另一位说「其实每轮都在写记录、只是没有时刻」。**后者是对的**（我核对了代码）。差别不小：它不是「漏采了」，而是「每轮都在采、每轮都采到空」——所以它不会自己好转，也不需要谁去修采集。

## 四、哪几件是同一个根

三组：**NewAPI 三条失败 + 那格在两种状态间跳 + 「已持续 7 分钟」老是归零**是同一个根（读上游的时间预算卡在临界点，加上告警没有防抖）；**669、2922、以及所有「触发 N 次」**是同一个根（那个数字是「每分钟重算一次条件」的轮数，不是发生次数）；**Sub2API 那格恒灰、开票那行恒定、服务器那行、以及日志里的「fake」**是同一个根——**界面和日志上的判据是别处事实的一份写死的、或者反过来实现的副本，事实变了它不会跟着变，也不会报错，只是安静地给你一个旧答案**。真正独立于这三组之外的只有两件：CPA 的快照供给断了（服务器侧的真故障），和 card_sync 被上游拒绝（上游/契约不一致，且理由被我们自己吞掉了）。
