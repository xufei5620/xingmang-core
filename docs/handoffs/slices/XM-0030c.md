## 四个刻意的决定

### 1. 清理与统计同一轮，且清理在前

顺序有语义：先把过期的推走，剩下的才是真正在等人的那些。反过来的话，一张
昨晚就该过期的单会被算成「等了 14 小时」，**告警报的是清理任务没跑，说出来
的却是没人审批**——一条指向错误方向的告警比没有告警更糟。

清理失败时**不统计也不写成功观测**，而是写一条 failed 观测，让既有的
「指标同步失败」规则去响。理由同上。

### 2. 告警报「最久那张等了多久」，不报队列长度

二十张刚提交的单不是问题，一张挂了六小时的才是。`PendingStats` 因此只返回
两个数字，而 `PendingCount` 只数**未过期**的——已过期的等的不是人、是清理
任务，混进来会让告警把「该清了」误报成「没人批」。

去重键只到队列（`:<environment>:queue`），不带单号：一个没人看的队列会一张单
一条告警刷屏，而它们说的是同一件事、要做的也是同一件事。

### 3. 门槛 4 小时

半个工作日：短于它会在午休和会议里误报，长于它就等不到当天处理。它同时
**短于 L4 单 4 小时的有效期**——告警必须在单过期之前响，否则人赶到时那张单
已经作废、只能让提交人重来。

### 4. 任务默认关闭

与其他任务相反。审批中心尚未在任何环境启用，一个对着空表跑的任务除了每 5
分钟写一条「队列长度 0」的观测之外没有作用，而**那条观测会让「审批中心已经
在跑」看起来成立**。注册条件是「开关打开 **且** `cfg.Approvals != nil`」。

`RunOnStart` 则是 **true**（与 Retention 相反）：它删不掉任何东西，只把已经
过期的单从 PENDING 推到 EXPIRED；而它顺带写下的观测越早写，告警的空窗越短。

## 测试

**`jobs/approval_expire_test.go`（6 条）** —— 清理在统计之前且观测内容正确；
清理失败时不统计、写 failed 观测、不带 `observed_at`（带对照组）；统计失败的
错误码可区分；没接服务时静默 no-op 且不写观测（带对照组）；观测写失败要冒
出来；空队列也要写观测。

**`alerts/approval_rule_test.go`（7 条）** —— 超门槛/恰好等于/差一秒；空队列
不响（带对照组）；五种残缺观测都不响；**JSON 往返之后仍认得出数字**
（先断言往返后确实不是 int64，否则这条用例测的还是假形态）；失败观测不判但
必须由「同步失败」规则报出来；门槛归一化。

**`alerts/consistency_test.go`（+1）** —— 指标键在 alerts 与 jobs 两处的字面量
必须逐字一致，且必须在 ops 白名单里。不一致的话规则**一条都不评估**：没有
报错，只是永远不响。

### 变异验证（五项）

| 变异 | 期望 | 结果 |
|---|---|---|
| 失败观测也拿来判 | 「失败观测不判」变红 | 红 |
| `numericField` 不认 float64 | JSON 往返那条变红 | 红 |
| 任务先统计后清理 | 顺序与「失败不统计」两条变红 | 红 |
| 去掉 `pending <= 0` | 「只有 age」子用例变红 | 红 |
| 去掉 `oldest_pending_age_seconds` 的缺失判断 | 期望变红 | **绿——那是死代码** |

**最后一项抓出了一段永不生效的守卫**，与 XM-0030b-api 里那道 `ttl <= 0` 同一类
错误：缺字段解出 0，而 0 低于任何合法门槛（`normalized()` 挡住了 0 与负数），
所以那道判断永远不改变结果。删掉了，并把注释改成说明「为什么只留一道」。
删完之后那几个子用例仍然全绿——因为它们断言的是**行为**（不响），不是某一行
代码存在。

## risks

- **`PendingStats` 每轮两条查询**，都走 `(environment, status, expires_at)`
  与 `(environment, status, created_at)`。审批队列是个位数到几十条的量级，
  没有为它建索引——**真到了需要索引的规模，先要处理的是没人看单这件事**。
- **观测是告警的唯一输入**。任务不跑 → 没观测 → 规则一条都不评估，而且
  不会有任何报错。Runbook §4.1 把这条排查路径写成了数据流的顺序。
- 告警**不区分环境内的多个队列**——目前一个环境只有一个审批队列，这个假设
  写在去重键里。
