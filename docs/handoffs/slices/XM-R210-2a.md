## Summary

This slice freezes a separately signed fleet manifest and active/closed database
binding inventory. Runtime code receives an independently configured public-only
keyring, validates the exact purpose/protocol and half-open validity windows,
then verifies a detached signature over the canonical payload digest. The
manifest checks replica/build capability parity; the inventory checks sorted
binding history and rejects two active owners for one binding. Pair verification
pins the inventory epoch/digest, change reference, active environment/cluster,
and non-overlapping/replayed artifacts.

No signing authority or private signing material is present in this slice.

## Contract and data-source mapping

| Contract field | Source/authority | Offline check |
| --- | --- | --- |
| `environment`, `worker_cluster_id`, `river_schema` | approved deployment manifest | lowercase ASCII ID grammar |
| `database_binding_hash` | later DBR-approved PostgreSQL binding reader | 64 lowercase hex; no host/DSN fallback |
| `epoch`, `nonce`, `change_ref` | release signer / append-only history | positive monotonic epoch, canonical nonce, printable change ref |
| `effective_manifest_hash` | R210-1 effective manifest | 64 lowercase hex and equal across build capabilities |
| `replicas[]` | release signer | unique, sorted logical IDs and strict `sha256:` build digests |
| `build_capabilities[]` | release build registry | every replica build known; contract/effective hash parity |
| `active_binding_inventory_epoch/sha256` | signed inventory artifact | exact epoch and canonical inventory digest |
| `bindings[]` | signed inventory snapshot | sorted rows and single-snapshot active-owner uniqueness; transition helper only checks caller-supplied append-only history |
| `signature_*` | independent repository-pinned public keyring | Ed25519, exact key ID/purpose/protocol/fingerprint |

Canonical payload bytes are `encoding/json` UTF-8 struct-field order with no
whitespace. Detached signatures cover
`<protocol>\nsha256=<payload digest>\n`; the envelope digest must equal the
canonical payload SHA-256. Keyring bytes are pinned by
`PinnedJobFleetKeyringSHA256` and are not selected from request/deployment
paths.

## Decisions

1. This is an explicitly **self-proposed, contract-only** §7.3 sub-slice. It
   does not claim approval for R210-2 Task 4/5 or any runtime wiring.
2. Manifest and inventory use separate signing purposes/protocols and separate
   public records. A key reused across purposes, a fingerprint mismatch, or an
   embedded key is rejected.
3. IDs use the design's ASCII grammar; hashes/build digests are lowercase and
   length-exact. Rows are required in canonical sort order instead of silently
   rewriting signed input.
4. Validity is UTC and half-open. A signed artifact may be issued before its
   activation window for staged rollout, but verification requires `now` inside
   the window and pair verification requires the manifest issuance to be inside
   the inventory window. Windows longer than the one-year policy cap fail
   closed.
5. Inventory snapshots reject duplicate active owners. The optional transition
   helper only checks that caller-supplied prior rows remain unchanged and that
   epoch/nonce advance; it does not model active→closed/reopened lifecycle
   events. Historical replay storage and lifecycle semantics remain an external
   signing/storage concern.

## Risks and follow-ups

- The one-year validity cap is a local fail-closed policy constant; changing it
  requires a reviewed contract decision.
- R210-2 Task 4 must consume these artifacts only after the separate DBR
  binding-read approval and must not infer identity from DSN text.
- Historical epoch/nonce storage, active→closed/reopened lifecycle records, and
  signing workflow remain external authorities; this package only validates
  caller-supplied prior state and a single inventory snapshot.
