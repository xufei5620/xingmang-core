# XM-UPSTREAM-VERSION-ALERT：上游版本变了要有人被告知

status: implemented（本地门禁见下）
branch: ai/claude/XM-UPSTREAM-VERSION-ALERT（自 release/v0.1-launch@8ca2910）
依据：2026-09-06 的生产事故（见开票仓库 `docs/handoffs/XM-INV-RC100-HARDENING.md`
与 `docs/handoffs/ACCEPTANCE-LOG.md` 的 RC100 条目），以及待办里的
「平台侧 Sub2API 版本观测 + 上游版本变化告警」。

## 事故里缺的那一块

运营在 Sub2API 后台点了升级，上游二进制从 `0.1.179` 变成 `0.2.1`。平台的连接器
兼容矩阵、开票代理的运行时钉子、运维手册里的三处版本号全都还写着旧值，而
**没有任何地方告诉任何人上游动过**。几天后按手册抬钉子时，四条采集流因为清单
不符崩掉、readyz 503 了两个小时。

值得说的是：**版本一直被观测着**。`ConnectorProbeWorker` 每轮都把上游自报的
`version` 与连接器的 `supported` 写进 `*.connector.health` 观测。缺的从来不是
数据，是「它变了的时候有人被叫醒」。

## 做了什么

新增告警规则 R6 `upstream.version.changed`：最新观测的上游版本，与同一条指标
历史样本里**最近一个不同的版本**不一致时报出来。severity 是 warning——版本变化
不是故障，是一个**要去核对的信号**（桥接契约、兼容矩阵、各处运行时钉子）；真正
的故障如果发生，会由别的规则以 critical 报出来。

## 五处判据，每一处都有它的反面

- **与「历史里最近一个不同的版本」比，不与「上一条样本」比。** 探测每轮都写一条
  样本，按上一条比的话这条告警只在变化后的一轮里存在，评估周期错开一次就永远看
  不见。往回找最近一个不同值，告警会一直在，直到有人处理它。
- **去重键带新版本。** 只带指标键的话，`0.1.179 → 0.2.1` 之后再 `0.2.1 → 0.3.0`
  会复用同一行，而人已经确认过前一条了——第二次变化就被静悄悄吞掉。
- **读不出版本不告警。** 没有 `version` 字段的观测（探测失败、连接器没实现
  `Version`、上游不报版本）不是「版本变了」。把缺失当成变化会在每次探测失败时都
  响一遍，而那时 R1 已经以 critical 说清「你现在是瞎的」——与既有的「`token_valid`
  缺失时不告警」同一条纪律。
- **同步失败态不评估。** 失败时 `value_json` 留的是上一次成功的旧值，拿它判「刚变
  了」是在用过期数据下现在的结论——与 R2/R3 不在失败态评估渠道规则同一条理由。
- **判据是「观测里有没有 version」，不是指标键叫什么。** 将来多一个连接器探测，它
  自动被覆盖，不必回来改代码；也避免了在 `alerts` 里硬编码 `jobs` 的指标键常量
  （那会成环）。

另外：连接器说 `supported=false` 时，详情里点名「兼容矩阵没有声明支持这个版本」
——那正是这次事故里最该被人看到的一句话。**没说 `supported` 与说了 `false` 是两回
事**，前者只是探测没给这个字段，不写成「不支持」。

## 测试

九条，每条钉住上面的一处判据：报出变化且带上下两个版本与 warning 严重度；去重键
末尾是新版本且带环境；版本稳定不报；第一次见到不算变化；观测没有 version 不报；
历史里没有 version 的样本被跳过、继续往前找；同步失败态不评估；`supported=false`
时详情点名兼容矩阵；没说 `supported` 时不写成「不支持」。

## follow_ups

- **连接器兼容矩阵还没声明支持 `0.2`**（待办里的第三小项）。这条规则会让它变得显眼：
  升级后第一次评估就会报「兼容矩阵没有声明支持这个版本」。矩阵本身要单独改一片，
  因为它牵涉 `connectors/sub2api` 的版本判定与契约测试。
- 平台页签上还看不到「当前上游版本」这个事实本身（只有变化时的告警）。在
  「连接与凭据」页签显示它是自然的下一步。
- 开票线的代理有自己的运行时钉子，不经平台的连接器探测；那一侧的版本一致性由
  RC100 的三处钉子与 `check-pending-spools.sh` 覆盖。
