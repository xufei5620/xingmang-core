# XM-PAY-STATUS-ROLLUP：把已经取回却被丢掉的区间汇总显示出来

status: implemented（本地门禁见下）
branch: ai/claude/XM-PAY-STATUS-ROLLUP（自 release/v0.1-launch@8ca2910）
依据：2026-09-06 Sub2API 缺口普查「支付与财务」区的
`[missing] 按原始状态的汇总（stats_by_status）在界面上的消费`，
以及原型的「最近事件表（成功充值 / 待处理 / 失败 / 退款 四行 + 金额/笔数）」。

## 为什么是这一条

充值订单页一直在解析上游返回的 `stats_by_status`（`api/finance.ts` 的
`listPlatformOrders` 里明明白白地取了它），然后**丢掉**。于是「今天一共成功了多少笔、
多少钱」这个最常被问的问题，只能靠人把表翻到底再自己加——而翻到一半算出来的数字是
错的，页面上还看不出它是错的。

`stats_by_status` 覆盖的是**整个查询区间**，不随翻页变化。它就是那张「最近事件表」
缺的数据源，一行代码都不用后端加。

## 做了什么

1. `lib/paymentStatusRollup.ts`：按 `bucketLabel` 把原始状态归进四个归一化桶
   （成功到账 / 待处理 / 失败 / 退款与冲正），笔数与金额相加，并**把落进每个桶的
   上游原始状态原样带出来**——归一化是为了好读，不是为了掩盖上游实际说了什么。
2. `components/PaymentStatusRollupTable.tsx`：渲染在逐笔表**之前**（先看整体，再决定
   要不要翻明细），标题旁写明它覆盖区间内全部 N 笔、不受翻页影响。
3. 挂进 `Sub2ApiOrdersPanel`。

## 三处刻意的诚实

- **整桶没有金额时显示「—」，不显示 0。** 一个桶里没有任何一条给出金额，与这个桶合计
  为零，是两件完全不同的事。
- **金额解析不出来时按未知处理，不当成 0。** 把读不懂的值算成 0 会让合计静悄悄变小；
  全程 `BigInt`，不经过 `number`（有一条测试用 9007199254740993 钉住精度）。
- **归不进四个桶的原始状态计入「未知」行，并在顶部单独报出来。** 上游加了新状态而我们
  悄悄丢掉，比显示一个陌生的桶名危险得多。

## 明确不做（都在这一页，都不是能自己决定的）

- **「净额」列**：`platformOrdersColumns.tsx` 里它已经是诚实留白，表头写着「净现金流
  公式尚未确定（需先确认手续费承担方与是否有未建模成本）」。这是**产品决策**，不是
  数据缺口——`amount - fee` 只是其中一种可能的口径。已登记进晨间清单。
- **「到账 / 完成时刻」列**：`payments.read.v1` 只给下单时刻，没有独立的到账时刻字段。
  拿 `created_at` 冒充到账时间，对一笔还在处理中的订单可能差任意长。需要上游先有这个
  字段。
- **资金对账面板、经营利润桥、利润核算子页**：都要「使用收入」，而它来自 NewAPI 收入库
  ——那条通道今天还没接（晨间清单第 ② 条：建只读角色并粘口令）。

## 测试

- 纯函数八条：多状态归桶且笔数金额相加、桶顺序固定且未知排最后、未知状态单独报出、
  整桶无金额是「未知」而非 0、部分有金额时只合计给出的那几条、金额解析失败按未知、
  大整数不丢精度、空汇总不报错。
- 面板三条：整区间的笔数与金额显示正确且写明「不随翻页变化」、未见过的状态在警示条与
  表格里各出现一次、整桶无金额显示「—」且不出现「¥0.00」。
