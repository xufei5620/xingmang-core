## 一、大白话：CPA 现在是怎么接的

**CPA 不是一个系统，是两个容器。** 一个是 `cli-proxy-api`（真正替你转发请求的代理），一个是 `cpa-manager-plus`（在旁边记账的侧车）。侧车把每一次调用记进宿主机上的一个 SQLite 文件 `usage.sqlite`——就是一个大号的本地账本文件，现在 **5.4GB**。

**平台跟 CPA 之间，一个字节的网络请求都没有。** 另外两个平台（Sub2API、NewAPI）是「打电话问」——平台调它们的只读 HTTP 接口，问一句答一句。CPA 是「复印账本」：

1. 宿主机上有个定时任务（`xingmang-cpa-snapshot.timer`），每隔一段时间把那 5.4GB 账本**整本复印**一份独立副本（用 SQLite 官方的 online backup，逐页复制，不是导出摘要、不是只复印最近几天）；
2. 复印件经过一整套自检（页面完整性、必需的 5 张表在不在、有没有残留的临时文件），确认合格后**原子替换**掉上一份；
3. 平台的两个容器（API 和 worker）把这份复印件**只读**挂进来；
4. 平台每 5 分钟从复印件里读四个数，写成四条指标。

**为什么要这么绕？不是设计偏好，是踩过坑。** 2026-08-31 试过直接把原账本目录只读挂进平台容器，四项读取全部失败（SQLite 的活动账本即使只读打开，也要往同目录写一个协调文件，只读挂载做不到）。09-01 你批准了「宿主机复印 + 原子发布」这个方案，并且当时就写死了几条禁令：不许改 CPA 原库、不许用 `immutable=1` 绕过、不许删协调文件、不许放宽容器权限。

### 和另外两个平台的六个差别

| 差别 | Sub2API / NewAPI | CPA |
|---|---|---|
| 数据怎么来 | HTTP 只读接口 | 整库文件复印 |
| 接入契约 | 已冻结 | 仍是**草稿**（DRAFT），两个业务口径没确认 |
| 开关在哪 | 后台可改（`core.connector_config`，每轮重读） | 只能改 `.env` 重新部署 |
| 有没有假数据档 | 有 fake 档（生产禁用） | 只有 `off` / `file` 两档 |
| 页面 | 原型画过 | **原型从来没画过 CPA 的内容**，只给了 5 个格子的名字 |
| 健康探测 | 有 `*.connector.health` 指标 | 没有——探测任务里写死只探那两个平台 |

### 这种接法的代价（部分为推算）

- **每一轮复印，实测约 2 分半 CPU**（09-01 验收记录：5.4GB 库首代 105 秒；你现测约 2.5 分钟）。
- **实际周期不是 5 分钟，是约 7.5 分钟一轮**（推算）。定时器用的是「上一次跑完之后再等 5 分钟」（`OnUnitInactiveSec=5min`），不是「每 5 分钟整点」。
- **每一轮至少把整库读 4 遍、写 1 遍**（按代码路径推导）：校验上一代 → 复制 → 校验复印件 → 发布后再校验一次。按 5.4GB 算，每轮约 21.6GB 逻辑读 + 5.4GB 写；按 7.5 分钟一轮外推，日均约 **4.1TB 读 / 1.0TB 写**（这个乘法是我算的，仓库里没有任何地方写过这条链路的 I/O 或磁盘预算）。
- **磁盘常驻约 16.2GB**（当代 1 份 + 历史最多 2 代），复印期间峰值约 **21.6GB**（临时文件就写在发布目录里）。
- **没有任何空间检查、CPU 限额、IO 限额、失败告警**。单元文件里只有一个 `Nice=10`（降 CPU 优先级），没有 `CPUQuota`、没有 `IOWeight`、没有 `OnFailure=`。
- **超时余量只有 2 倍**：允许跑 5 分钟（`TimeoutStartSec=5min`），实测 2 分半。账本继续长大就会先撞这堵墙。

### 这种接法的风险（其中一条正在发生）

**正在发生的**：定时器从 2026-09-01 22:47 之后就不再循环了（状态是 `active (elapsed)`、下次触发 `NEXT n/a`）。09-06 13:52 那次是人手工点的。所以快照冻在 **09-06 13:53**，四条 CPA 指标从 09-06 14:33 起连续告警约 **49 小时**。

这件事暴露了三个结构性问题：

1. **定时器没有绝对时间锚点，也不会自愈。** 它只有「开机后 2 分钟」和「上次跑完后 5 分钟」两个触发条件，没有「每天几点」。一旦丢了下一次触发点，只有重启主机、或下一次生产部署跑到最后一步重新启用，才会活过来。
2. **部署门禁看不出这个状态。** 门禁只问两句：「定时器启用了吗」「定时器活着吗」——这两句在 `NEXT n/a` 的状态下**都是 yes**。门禁测的是进程状态，不是「下一次什么时候跑」。这道闸对这次故障是恒绿的。
3. **页面上分不清「我们坏了」和「对面冻住了」。** 平台每 5 分钟都成功一次，但它读到的时间戳是**复印件里记的时刻**，不是「我们最后一次去读是什么时候」。所以宿主机复印停了，页面表现和「平台采集程序死了」完全一样。09-08 的复盘报告原话：「界面分不清『我们的采集程序死了』和『上游数据冻住了』」。

**还有一条没发生但机制上敞着的**：快照的代号（generation）是随机数、不可排序，平台写观测时是无条件覆盖时间戳，没有「新的不能比旧的老」这道闸。如果把一份更旧的复印件放回去，平台会照单全收，只表现为「更陈旧」，不会报错。（生产上有没有真发生过，我查不到。）

## 三、「重新规划」可能指的三层

以下只列**要动什么**和**依赖什么**，不给推荐、不排优先级。三层可以单独发生，也可能同时发生。

### ① 换数据通道（换掉「整库复印」这个取数方式）

**要动的东西：**
- 连接器 `connectors/cpa` 现在只有一个文件后端（`NewFileClient`），要加一个新后端就要重写取数层，五个能力（版本 / 健康 / 用量 / 密钥用量 / 账号健康）逐个重接。
- 契约 `contracts/connectors/cpa.read.v1.md` 要改（它现在还是 DRAFT，按 §10 可以直接改文件不发 v2）。
- 模式枚举现在只认 `off|file`（`cmd/platform-api/cpa.go:21-41`），要加档就要动启动期校验。
- 宿主机那套东西（复印程序 `cmd/cpa-snapshot` + 两个 systemd 单元 + 部署脚本里 4 个阶段 + compose 的只读挂载）要么下线要么保留成备份路径。
- 定时器的自愈问题、部署门禁的判据问题（现在只看「活着」不看「下次什么时候跑」），如果通道不换，这两条是独立的、可以单独修的。

**依赖的东西（都不在平台这边）：**
- **必须先回答**：`cpa-manager-plus`（127.0.0.1:18317）到底有没有一个可读的 HTTP 接口。这是仓库里明确写着「未经验证」的一条，不是已否定。要么看上游仓库 `github.com/seakee/CPA-Manager-Plus`，要么你来给。
- 如果走 `cli-proxy-api` 的管理接口：要过三道审批（R213-2/3 隔离验收、R2-14 插件审批、单独的能力审批），而且那把管理钥匙一把通吃读写配置和带凭据外呼——平台自己的边界契约现在是全禁的。另外还要先拿到目标版本的**真实路由清单**（现在契约里是全 0 占位）和**真实运行版本证据**（现在钉的 1.0.0 vs 生产的 `:latest`）。
- 如果想读 `/usage-queue`：那是**破坏性**的取数（读走就从队列里删了），而且和侧车自己的消费者共用同一个队列——等于从侧车嘴里抢数据。平台的设计文档给它列了四项前置（单持有者租约、明确的计数/游标语义、预算与退避、读之前下游已落库），四项目前一项都没有。
- 「只读数据库账号」这条路**技术前提不成立**：CPA 的存储是宿主机上的一个文件，没有账号/角色这个东西。
- 「直接只读挂原文件」这条路**已经被生产证伪**（08-31，四项读取全失败），而且 runbook 明令禁止回滚到这个做法。

**顺带会解决 / 不会解决的：**
- 换通道**不会自动解决**「页面上分不清是我们坏了还是对面冻住了」——那个是观测字段的问题（`SyncedAt` 写了库但没送到页面），要单独修。
- 换通道**可能顺带解决**磁盘/CPU 成本，也**可能不解决**（取决于新通道是什么）。

### ② 换指标与页面（数据通道不动，改上层）

**在现有通道下可以做到的（数据已经在手里，只是没往上送）：**
- 每个模型花了多少钱——连接器已经算出来了，指标层丢掉了，前端类型里甚至已经声明了字段但没有组件渲染。
- 日期选择器——接口已经支持指定日期，前端没暴露。
- 「我们最后一次尝试是什么时候」——这个字段已经写进数据库了（`SyncedAt`），只是没进新鲜度契约、没送到页面。修它要动后端的新鲜度结构 + 前端的契约类型 + 状态矩阵那一格的判词。
- 页签改名 / 合并 / 删除——「用户管理」名不副实（一行是一把密钥不是一个用户）、「渠道管理」和「支付与财务」两格结构性没内容。改动涉及：导航定义（`navigation.ts:459-473`）、信息架构文档（`ADMIN-IA.md:49,115`）、平台目录文案（`platforms.ts:66-69`，现在还写着「推广投放与结算：代理商」，跟实际完全不是一回事）、阶段徽标（M4 / M1.5）。
- 被管系统清单里补上 CPA 这一条（现在只有另外两个平台）。
- 契约 §9 与代码的漂移（probes / history 两个子页签实际会打到一个对 `cpa` 硬拒绝的后端）——要么改代码回落占位，要么改契约承认现状。

**在现有通道下做不到的（数据源里根本没有）：**
- 密钥配额、剩余额度 —— 账本里没有这个字段；配额若存在，只可能在 `config.yaml` 里，而那是明令绝不读的文件。
- 限流 / 429 / 退避 / 重试 —— 零数据源。
- 代理可用性 / 成功率 / 时延 —— 账本里没有状态码和时延列。
- 渠道 ↔ 模型的映射、供给侧配置 —— 「渠道管理」那格空着就是因为这个。
- 支付 / 充值 / 对账 —— 「支付与财务」那格空着就是因为这个。
- 以上五项要么依赖 ①（换通道），要么依赖 ③（上游改）。

**依赖的东西：**
- **最关键的依赖是你**：仓库里**没有任何一份文档写过「CPA 该管什么」**。原型是 todo 占位，信息架构只给了 5 个格子的名字，现在这三块真实内容是 XM-CPA0 直接照着数据形状搭的（面板注释里原话：「没有原型可对齐……不编原型没画过的格子」）。所以「设计意图与实现的落差」这件事，落差不在实现偏离了设计——**这一段根本没有过 CPA 专属的设计意图**，只有一份从 Sub2API 复制来的页签骨架。
- 业务日时区和货币两个口径（契约 §8）没定之前，页面上所有「今天」的数字都带一个未核对的前提。

### ③ 上游本身要变（CPA 那边改，平台被动跟）

**可能的形状（都需要上游动手，平台这边只能提要求）：**
- **账本瘦身 / 保留策略**：5.4GB 是复印成本的直接来源。上游那张表存了多久、能不能归档、能不能分区——仓库里零记载。侧车自己**已经有一套汇总机制**（`usage_rollup_checkpoints` 表存在），但平台的契约明确不读它，也没写为什么不读。
- **让侧车直接写外部存储**：比如让 `cpa-manager-plus` 把用量写进平台的数据库，或者写一个可拉取的汇总文件。这样整库复印这条链路可以整个下线。能不能配，仓库里查不到。
- **补齐缺失的数据**：状态码、时延、配额、限流、封禁 —— 这些是「CPA 到底有没有」的问题，不是「平台能不能读到」的问题。
- **升级到明确版本**：现在两个容器都是 `:latest`。任何依赖管理接口的方案都要先钉版本，因为路由清单和契约要对着具体版本冻结。

**依赖的东西：**
- 上游仓库或上游作者。本机上**没有** `cli-proxy-api` 和 `cpa-manager-plus` 的源码克隆（K 盘只有 sub2api-src、newapi-src），仓库里也没有它们文档的副本，只有两条外链 URL（`help.router-for.me/management/api` 和 `/plugin/development`），而且引用时都带同一句限定语：这是 2026-08-29 的时点快照，实施前必须对目标版本重新核对。
- 另外，R2-13 / R2-14 那两条线（CPA 管理面边界契约 + 插件准入治理，合计约 4500 行 Go + 3 份契约 + 2 个命令行工具 + 3 份 runbook）**已经写好并合入了，但零运行时接线**——它们只被自己的命令行工具引用，没有任何路由、任务或页面用到。它们当初被定为「M4 CPA 接入的前置门」。这批东西在重新规划里算前置门、算沉没成本、还是该冻结，需要你定。
