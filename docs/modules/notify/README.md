# notify —— 企业微信通知的信封

> 设计稿 `docs/superpowers/specs/2026-09-06-xm-notify-envelope-design.md`（XM-NOTIFY-ENVELOPE）
>
> **要给一个新功能接通知？看 `INTEGRATION.md`，不是这一份。**
> 这一份讲信封为什么长这样（写给改 notify 包的人）；`INTEGRATION.md` 讲怎么接
> （写给做功能的人）；`CATALOG.md` 讲收到每条消息代表什么（写给运营）。

平台有三条互相独立的企业微信群机器人通道，各有各的凭据引用、各写各的格式。运营把同一个
Webhook 地址填进了三个凭据——这是合理用法——于是三种消息落在同一个群里，而它们谁也没说清
自己是什么。本包统一"头部与尾部"，正文仍由各域自己写。

## 通道与凭据（三条通道不合并）

| 域 | 徽标 | 凭据引用 | 触发者 | 处理入口 |
|---|---|---|---|---|
| 告警 | 【星芒·告警】 | `secret://alerts/wecom-webhook` | `platform-worker` 告警评估轮次 | 管理后台 → 告警与故障 |
| 卡片 | 【星芒·卡片】 | `secret://cards/notify-webhook` | `platform-api` 的 Infini 回调 | 管理后台 → 卡片管理 |
| 接码 | 【星芒·接码】 | `secret://sms/notify-webhook` | `platform-api` 的取码调用 | 管理后台 → 接码中心 |
| 开票 | 【星芒·开票】 | 待定（见设计稿 §6） | 待实现 | 管理后台 → 开票 |

**为什么不合并**：三个领域的字段完全不同（告警有规则/持续时长/去重键，卡片有卡号掩码/商户/
金额，接码有号码/供应商）。为了共用把它们并进一个结构体，会让任一方加字段时都要改另一方；
共用的其实只有"群机器人收 markdown"这一个事实。**想发到同一个群，把同一个地址填三遍即可**；
想分开发（比如卡片 3DS 的码只给自己看），填不同地址即可——这正是三个凭据存在的意义。

## 一条消息长什么样

```
【星芒·告警】<font color="warning">严重</font> · production
> 标题：指标 sub2api.revenue.daily 同步失败
> 规则：metric.sync.failed
> 状态：OPEN
> 首次发现：2026-08-27T05:00:00Z
> 最近发现：2026-08-27T05:03:00Z（累计 4 次）
> 指标：sub2api.revenue.daily
> 详情：来源 sub2api-prod，错误码 timeout。
> 编号：XM-ALERT-metric.sync.failed
> 处理：管理后台 → 告警与故障
```

收件人一眼能答出五件事：哪个域、多严重、哪个环境、编号是什么、该去哪处理。

## 三条排版纪律

1. **只有闭集用 markdown 语法**。域徽标、严重度、环境、编号、处理入口来自封闭枚举与我方文案，
   给它们上色是安全的。标题、详情、商户名、指标键这些**上游决定的字符串**一律进 `> ` 引用块
   且不带任何标记——带标记就得转义，漏转义的后果是排版错乱甚至整条发不出去。`> ` 不会被内容
   中任何字符提前闭合，纯装饰、零转义负担。
2. **长度按字节截断**（企微 `content` 上限 4096 **字节**，不是字符；UTF-8 下一个汉字 3 字节，
   按 rune 截仍会越界，上游直接拒收整条消息）。截断只发生在正文：头部与编号/处理两行永远保留，
   一条被截到看不出是什么的消息等于没发；截断处明说"（正文已截断）"。
3. **凭据绝不进消息，也绝不进错误串**。企微 Webhook 地址把鉴权 key 放在查询参数里，
   **整个地址就是凭据**（宪法 7 条）。

## 严重度

| Severity | 中文 | 企微 color | 用在哪 |
|---|---|---|---|
| critical | 严重 | `warning` | 告警规则判定为 critical |
| warning | 警告 | `warning` | 有时效或要立刻动手：验证码、卡片状态变更、失败的授权 |
| info | 通知 | `comment` | 周知：一笔已授权的消费 |

企微只认三种颜色，没有独立的红与橙：critical 与 warning 同色。**颜色不是唯一区分手段**，
中文词才是。

## 编号

`XM-<域大写>-<Kind>`。它是**类型编号，不是实例编号**：同类事件共用一个编号，群里搜它能捞出
同类的全部历史。实例的唯一标识（告警的 dedup_key、卡片的账号与掩码）已经在正文里。

## 加一条新通知

1. 选域（没有合适的就在 `notify.Domain` 加一个，同时补徽标与本文的表）。
2. 定 `Kind`：域内稳定事件键，进编号，**只增不改**（改名等于让群里的历史搜索失配）。
3. 定严重度：按"要不要立刻动手"，不按"这件事重不重要"。
4. 组装 `Envelope` 交给 `RenderWeComMarkdown`；正文用 `Line{Label, Value}`，空值行会被自动省略。
5. 若字段来自一张 map，用 `SortedLines` 保证渲染顺序确定——map 迭代顺序随机会让同一条事件
   两次渲染出的消息不一样，"这条我是不是收到过"就无法判断。
