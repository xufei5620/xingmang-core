# 企业微信消息目录：收到每条消息代表什么

> 配套：`docs/modules/notify/INTEGRATION.md`（**新功能要发通知时照那份做**：
> 该不该发、选哪种模型、每种消息的模板、噪声预算）、
> `docs/modules/notify/README.md`（信封为什么长这样）、
> `internal/platform/alerts/README.md`（告警规则的判据细节）。
> 本文档由 `internal/platform/notify/catalog_test.go` 钉住完整性：
> **新增一种消息而没写进这里，测试会红。**

这份文档给的是**收件人**要的东西：群里弹出一条消息，它是什么、要不要现在动手、
去哪处理。所有示例都不是手写的，是把真实渲染函数跑出来的输出抄进来的。

## 先看这四件事

**1. 一条消息的前两行就够判断了。**

```
【星芒·告警】<font color="warning">严重</font> · production
> 标题：指标 sub2api.revenue.daily 同步失败
```

第一行三段：**哪个域**（告警/卡片/接码/开票）、**多严重**、**哪个环境**。
最后两行永远是 `编号` 与 `处理`——编号用来在群里指认"就是那条"，
处理告诉你去后台哪一页。

**2. 严重度按"要不要立刻动手"分，不按"这件事重不重要"。**

| 徽标 | 含义 | 你该做什么 |
|---|---|---|
| <span>严重</span> | 已经在丢数据或已经不可用 | 放下手里的事 |
| <span>警告</span> | 有时效或会恶化 | 今天之内处理 |
| <span>通知</span> | 周知，记录用 | 看一眼即可 |

**3. 四个域可能落在同一个群，也可能不落在同一个群。** 它们是四条独立通道、
四个凭据引用（`secret://alerts/wecom-webhook`、`secret://cards/notify-webhook`、
`secret://sms/notify-webhook`，以及开票系统自己那一条——它填在**开票管理端的**
**设置页**里，不在平台凭据页，理由见下面第四节）。填同一个地址就同群，
填不同地址就分开——比如卡片 3DS 的验证码只想给自己看时。

**4. 消息里永远不会出现这些**：完整卡号（只有掩码）、完整手机号（只有掩码）、
开票抬头/税号/银行账号/地址/电话（加密存着，推送根本读不到）、
任何凭据或 Webhook 地址（连投递失败的错误里都没有）。
理由是同一条：**群消息留在聊天记录里，那不是我们能控制的存储。**

## 一、告警（`secret://alerts/wecom-webhook`）

发出者是 `platform-worker` 的告警评估轮次（默认每 60 秒一轮）。

### 什么时候会响，什么时候不会

这一条比规则本身更容易被误解：

- **一条告警只在"首次触发"时推一次。** 它持续满足条件的每一轮，只把
  `累计 N 次` 加一，**不会再推**——否则同一件事每分钟一条，群就废了。
- **恢复不会推。** 待投递队列只取 `OPEN` / `REOPENED` 两种状态。
  想知道"好了没有"，去管理后台的告警与故障页看，那里有恢复时刻与持续时长。
  （要不要加恢复通知是产品决策，见文末。）
- **静默窗口到期而问题还在，会再推一次**——被捂住嘴的那段时间不算数。
- **解决之后又复发，会再推一次**：那是一条新告警，状态 `REOPENED`。

### 示例

```
【星芒·告警】<font color="warning">严重</font> · production
> 标题：指标 sub2api.revenue.daily 同步失败
> 规则：metric.sync.failed
> 状态：OPEN
> 首次发现：2026-09-06T07:55:00Z
> 最近发现：2026-09-06T08:00:00Z（累计 4 次）
> 指标：sub2api.revenue.daily
> 详情：来源 sub2api-prod，错误码 timeout。
> 编号：XM-ALERT-metric.sync.failed
> 处理：管理后台 → 告警与故障
```

### 七条规则

「规则」那一行的取值只有这七个。**它就是这条消息的分类**。

| 规则键 | 标题 | 严重度 | 什么情况下响 | 什么时候自己好 | 你该做什么 |
|---|---|---|---|---|---|
| `metric.sync.failed` | 指标同步失败 | 严重 | **连续 3 轮**采集失败（10 分钟以内的抖动不报） | **连续 3 轮**不再失败（成功一两轮不算恢复） | 看详情里的错误码；鉴权类要查凭据，超时类先看上游活着没有 |
| `metric.sync.consecutive_failed` | 同步长期失败 | 严重 | 当前正在失败，且最近 12 轮采集里**失败 ≥ 9 轮**（滑动窗口，中途成功一两次不清零） | 窗口内失败次数回落到 9 次以下 | 比上一条更重：这一小时一直在坏，按故障处理 |
| `metric.data.stale` | 指标数据陈旧 | 警告 | 没失败，但数据太久没更新（超阈值 + 若干个采集周期） | 数据重新进入新鲜阈值 | 采集器可能没在跑；看后台任务页那条同步任务的最近一次运行 |
| `channel.token.invalid` | 渠道 token 失效 | 警告 | 上游渠道清单里该渠道 `token_valid` 明确为 false | 恢复为 true，或该渠道从上游消失 | 去上游后台换 token；这条按渠道去重，多个渠道会有多条 |
| `channel.balance.low` | 渠道余额不足 | 警告 | 余额低于阈值（按环境可配） | 余额回到阈值之上 | 充值。阈值不合适就调 `XM_ALERT_BALANCE_THRESHOLD_MINOR_UNITS` |
| `upstream.runway.low` | 上游可用天数不足 | 警告（天数更少时升为严重） | 余额 ÷ 近 7 个业务日的日均消耗 ≤ 阈值天数 | 天数回到阈值之上，或算不出天数了 | 按天数安排充值。**算不出来就不报**（余额读不到/无消耗/停用） |
| `upstream.version.changed` | 上游版本变化 | 警告 | 这次探测到的上游版本与上一次**不同**，且这个版本还没有人核对过 | 有人执行 `alerts.upstream_version.acknowledge` 核对了这个版本（下一轮自动解决），或不再变化 | 确认是不是计划内升级；详情会说兼容矩阵认不认这个版本，不认就要先核对源码再补矩阵。核对完执行那个 Action，别让它靠证据过期自己消失 |
| `approval.pending.too_long` | 审批单挂太久 | 警告 | 最久那张未过期的待审批单已等待 ≥ 4 小时 | 最久那张降回门槛内（有人批了或驳了），或队列清空 | **去看那张单**，不是去查日志：它说的是一件本该发生的变更还没发生。处置见 `docs/runbooks/APPROVAL-QUEUE.md`，含「审批人失联怎么办」 |

**读这张表时要注意的三处**：

- `metric.sync.failed` 与 `metric.data.stale` **不会同时对同一条指标响**：
  失败的优先级高于陈旧，一条记录只落在其中一个状态上。
- `upstream.version.changed` 的详情里如果写着**兼容矩阵没有声明支持这个版本**，
  那说的是**我们这边**没跟上，不是上游坏了——两者处理方式完全不同。
- `approval.pending.too_long` **整个环境只有一条**（去重键不带单号）：
  一个没人看的队列会一张单一条告警刷屏，而它们说的是同一件事、要做的也是
  同一件事。所以看到它的时候，队列里可能不止一张单在等。

## 二、卡片（`secret://cards/notify-webhook`）

发出者是 `platform-api` 收到的 Infini 回调。**卡片事件是一次性的**，不像告警
那样有"仍然满足条件"，所以没有去重、没有持续时长、没有恢复。三种：

### `challenge`——验证码 / 待验证（警告）

```
【星芒·卡片】<font color="warning">警告</font>
> 标题：验证码 889201（acct-01 · **** 4321）
> 有效期：剩余约 5 分钟
> 编号：XM-CARD-challenge
> 处理：管理后台 → 卡片管理
```

码放在标题里，因为正在付款的人要一眼抓到它。**有效期写的是"剩余多少分钟"
而不是过期时刻**：你看到消息时往往已经过了一分钟，而一条过期的码和一条有效的
长得一模一样。

上游有时不给码。那时标题是 `卡片待验证 …`，并多一行
`说明：上游未给出验证码，请到管理端或 Infini 后台查看`——不会推一条空的"验证码："。

### `transaction`——交易（失败是警告，其余是通知）

```
【星芒·卡片】<font color="warning">警告</font>
> 标题：卡片消费 acct-01 · **** 4321
> 商户：OPENAI *CHATGPT
> 金额：20.00 USD
> 状态：失败
> 原因：insufficient balance
> 编号：XM-CARD-transaction
> 处理：管理后台 → 卡片管理
```

标题里的动词来自交易类型：消费 / 冲正 / 退款 / 充值 / 赎回。
**`状态：失败` 时才是警告**，一笔正常授权是通知。
`原因` 是上游原文，不翻译——"余额不足"这类原因正是你要拿去处理的东西。
没见过的类型或状态**原样显示英文**，不会被藏起来。

### `status_change`——卡状态变更（警告）

```
【星芒·卡片】<font color="warning">警告</font>
> 标题：卡片状态变更 acct-01 · **** 4321
> 当前状态：已锁定
> 编号：XM-CARD-status_change
> 处理：管理后台 → 卡片管理
```

状态取值：初始化 / 处理中 / 已激活 / 已锁定 / 删除中 / 已删除。
**「已锁定」和「已删除」要当回事**——卡不能用了，挂在上面的订阅会连着失败。

## 三、接码（`secret://sms/notify-webhook`）

发出者是 `platform-api` 的取码调用。只有一种：

### `code`——收到验证码（警告）

```
【星芒·接码】<font color="warning">警告</font>
> 标题：验证码 553012（+86 138****5678）
> 号码：+86 138****5678
> 验证码：553012
> 供应商：sms62
> 时间：2026-09-06 08:00:00 UTC
> 编号：XM-SMS-code
> 处理：管理后台 → 接码中心
```

号码只有掩码。**没配地址就不推**，这不是错误——运营还没填而已。

## 四、开票（地址填在开票管理端 → 设置 → 企业微信通知）

发出者是**开票系统**，不是平台。它用自己的 Webhook 凭据、自己的发件箱，
不经过平台（理由见 `docs/handoffs/slices/…` 与开票仓库的
`docs/handoffs/XM-INV-SUBMIT-NOTICE.md`）。只有一种：

### `request.submitted`——用户提交了开票申请（通知）

```
【星芒·开票】<font color="comment">通知</font> · production
> 标题：新的开票申请 INV-20260906-0031
> 申请单号：INV-20260906-0031
> 金额：1280.00 CNY
> 来源：sub2api
> 状态：待审核
> 提交时间：2026-09-06T08:12:00Z
> 编号：XM-INVOICE-request.submitted
> 处理：管理后台 → 开票 → 申请审核
```

**是 `通知` 不是 `警告`**：有人提交了申请是周知，不是要立刻动手的事。
真正需要动手的是"待审核积压超过 12 小时"，那是另一条规则、另一个严重度，
今天还没有（依赖跨线只读契约 CR-0002）。

**这条消息里没有任何抬头、税号、银行账号、地址、电话**——它们在申请里是加密
存着的，通知的取数只读上面这几个非 PII 字段。这一条由一个反射测试钉死：
将来有人往通知载荷里加字段，必须先撞到那条测试。

**投递失败会重试**：30 秒起指数退避、1800 秒封顶，第 8 次后停在 `failed` 并留痕。
一条两小时前的"有人提交了开票申请"已经不是通知而是历史。

**默认是关的**，但开启不用碰服务器：开票管理端 → 设置 → 企业微信通知，粘贴
群机器人地址 → 保存 → 点「发送测试消息」确认。改地址同理，**改完下一条通知就
用新的，不必重启**；此前攒下的会一起补发（发件箱一直在入队）。

地址存在开票系统自己的库里（密文），页面只显示 sha256 指纹前缀供核对，
**永不回读地址本身**。它不在平台的凭据页上：开票通知是开票系统自己发的，
用自己的凭据——这正是 ADR-018 通道隔离要的效果，把地址放平台那边反而要造一条
"平台向开票递凭据"的路。

## 收不到消息时按这个顺序查

1. **这个域配地址了吗。** 四个域四个凭据引用，配了哪个只有哪个会推。
   管理后台 → 设置 → 凭据管理能看到每条配了没有。
2. **这条事件本来就不推吗。** 告警的恢复不推；卡片的正常授权推但是「通知」级；
   一条已经推过的告警在持续期间不会重推。
3. **投递失败了吗。** 告警有投递状态（`pending`/`delivered`/`failed` 与失败原因），
   在告警详情里看得到。开票的通知走
   `GET /api/v1/admin/invoice-requests/{id}/notices`（管理员专用，
   XM-INV-NOTICE-VIEW）——它给出状态、尝试次数、下次重试时刻与失败短码。
   管理端**申请详情抽屉里也有一格「企业微信通知」**（XM-INV-NOTICE-UI），
   直接看得到状态、尝试次数与失败短码，不必自己调接口。还没有的是"最近失败
   的通知"这种全局列表——今天只能按申请查。
4. **机器人还在群里吗。** 企业微信的失败放在响应体里，HTTP 200 也可能是失败
   （`errcode` 非 0）。我们把这种情况按失败记录，不当成功。

## 还没有的（都要产品负责人拍板，不是技术卡点）

- **告警恢复通知**。今天只推"开始"不推"结束"。加了之后群里消息量翻倍，
  值不值得由运营定。
- **开票的其余事件**。今天只有"提交"。审核通过、开具完成要不要也推？
  每多一种就多一份群消息，太吵会让人把整个群静音——那比不发还糟。
- **待审核积压 > 12 小时**。属平台侧告警规则，依赖 CR-0002 冻结。
- **开票通知的全局失败列表**。今天只能按申请查（详情抽屉里那一格）；
  想问"最近有没有发失败的"还得查库。
- **带序号的告警号**（形如 `AL-2609-0007`）。今天的编号是规则键，同一规则的
  多条告警编号相同。要真正的流水号需要后端加字段——前端自己生成会让两个人
  看到不同的号。
