## Headline finding: today's tokenmap cannot supply a stable UserRef

`tokenmap.json` in this run has 3572 entries, all shaped `<username-or-email>@<source>` (239 `@newapi`, 3333 `@sub2api`, 0 with an unrecognized suffix). That shape has no field for an upstream numeric/opaque user id. `cmd/reqlog-recorder/tokenmap.go`'s own export queries only `SELECT` username/email from both upstream databases, never `id`, even though both queries already `JOIN` on it. **This is a schema-level fact** - true of any tokenmap this recorder produces, not just this sample - and it means Task 8 cannot ship a `platform.UserRef{Platform, ID}` from this pipeline without first changing that export query to also select the upstream id. See `retention_and_association.json` for the counts backing this.

## Cursor semantics

Cursor is the opaque string "reqlog:<offset>" (connectors/reqlog/fake.go cursorPrefix + encodeCursor/decodeCursor) wrapping a plain integer offset into a result set that connectors/reqlog/file_client.go's matchedSummaries fully re-scans and re-sorts (by OccurredAt, descending) on EVERY call, before the offset is applied. It is not a stable position against concurrent writes: a request recorded between page 1 and page 2 of the same query shifts every later offset by one, so a record at the old page boundary can repeat across pages or be skipped entirely - the same class of hazard already documented for the platformusers real client's offset-based Sub2API/NewAPI pagination (docs/handoffs/slices/XM-USERS-REAL.md). This is a fact read from source, not derived from the sample data in this directory - it does not change from one capture run to the next.
