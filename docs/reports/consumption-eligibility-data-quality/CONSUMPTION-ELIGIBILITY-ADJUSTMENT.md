# 充值且已消费开票口径：数据质量与调整报告

快照时间：2026-08-21 06:04（Asia/Shanghai）

范围：FiberState 上运行的 Sub2API 0.1.178 与 New API rc.25

执行边界：只读聚合；未读取或输出任何用户、邮箱、订单、日志正文或凭据。

## 技术结论：新口径正确，但历史数据不能自动重建

- 可开票金额应改成：**真实支付资金中已经实际消费的累计现金金额，减去退款冻结、待审预占和已开票金额**。
- 当前版本按支付完成金额产生可开票上限，不能满足“充值且已消费”规则，生产部署已暂停。
- 两套上游都只有混合余额，消费记录没有原始充值批次外键。直接对历史记录套用 FIFO，会把假设当成税务事实。
- 安全可实施方案是设置切点：切点前余额全部视为不可开票旧余额；切点后才建立完整的现金、非现金、消费和分摊账本。

## 口径与账本粒度

### 现金资金批次

一笔经过外部支付证据核验的真实支付。必须同时保存：

- 人民币现金金额（分）；
- 上游实际发放的服务额度单位；
- 支付、退款和来源版本快照；
- 已累计消费的服务额度与对应现金分。

充值赠送不能混入现金服务额度。若支付100元获得150额度，现金和赠送必须拆成
两个不同的批次。

### 非现金资金批次

以下全部不可开票：

- 切点时的历史余额；
- 充值赠送、活动返利、邀请返利；
- 兑换码、签到奖励、管理员加款；
- 无法由已知事件解释的正余额差额。

### 消费事件

一条消费事件必须有稳定来源 ID、用户、时间、服务额度扣减和计费类型。
订阅消费与钱包消费必须分开。零金额、退款回补、重试和冲正不能当作新消费。

### 消费分摊

规则冻结为：

1. 非现金余额优先消耗；
2. 现金批次按 FIFO 消耗；
3. 现金换算使用累计比例和精确有理数舍入；
4. 本次现金金额等于新的累计结果减去上次累计结果，不能逐请求独立四舍五入；
5. 任何来源断层都会冻结新增可开票金额。

## 推荐数据库调整

在现有 `funding_lots` 与 `invoice_allocations` 基础上新增：

- `source_usage_events`：不可变消费事实、来源游标、版本和去重键；
- `source_credit_events`：非现金信用、管理员调整和余额基线；
- `consumption_allocations`：消费到现金/非现金批次的分摊；
- `funding_lot_consumption_state`：累计服务额度与累计现金舍入状态；
- `balance_reconciliation_checkpoints`：上游余额守恒检查；
- `eligibility_freezes`：日志断层、无法解释负差额或来源漂移的冻结原因。

现有 `invoice_allocations` 继续负责并发预占和防重复，但可分配上限从
“支付金额”改成“已经消费的现金金额”。

用户不必一次开完全部可用金额：例如累计已消费现金为600元，可以先申请400元，
剩余200元以后再申请。每次提交只需满足单次最低200元，且所有待审预占与已开票
合计不得超过已经最终化的累计现金消费金额。

## 切点迁移方案

1. 记录切点时间与两套上游运行版本。
2. 将每个用户切点余额导入 `LEGACY_NON_INVOICEABLE`，永远不可开票。
3. 从切点后的新支付、非现金信用、余额消费和退款开始同步。
4. 每轮按事件时间分摊，并与上游当前余额做守恒对账。
5. 无法解释的正差额按非现金入账；无法解释的负差额不产生现金消费，直接冻结。
6. 支付、非现金信用、消费和余额四条流分别上报扫描水位；只有共同水位越过事件时间
   与安全延迟后，现金消费金额才可进入可申请额度。
7. 共同水位之后又出现的迟到事件不得静默改写已预占或已开票金额；降额时冻结用户与
   资金批次，已开票暴露进入退款/红冲关注队列。
8. 日志关闭、清理、游标跳跃、事件重写、同时间戳因果顺序无法证明或运行版本漂移时
   fail-closed。
9. 切点前历史不提供自动或人工补开入口，不能按当前余额倒推。

切点后新注册的上游账号不在原始余额成员中。余额流必须用签名的 `baseline_member=false`
证明这一点。该证明意味着账号在全站签名基线中不存在，因此开票账本以全站切点的
零余额为起点，重放全站切点后的签名支付、非现金信用和钱包消费；首次完整余额只作为
守恒检查点，不再吞掉绑定前的有效事实。订阅不属于钱包 FIFO，当前来源契约也不能把
订阅购买无歧义关联到实际使用，所以 V1 仅保留订阅支付审计，始终不可开票。

## 为什么不能直接重算历史

- Sub2API 管理员调账通常写入兑换记录，但余额更新与记录写入不是同一事务；
  记录失败时余额仍可能已经变化。
- Sub2API 支持主动清理消费日志，现网已经出现明显历史留存切点。
- New API 可以关闭消费日志，管理员额度和活动额度没有不可变资金流水。
- New API 的三种累计消费口径当前并不相等。
- 两套消费表都没有 `funding_lot_id` 或 `payment_order_id`。

因此更复杂的 FIFO 算法只能产生更复杂的估算，不能补回缺失证据。

## 自动门禁与测试要求

- 消费事件主键和来源复合键唯一；
- 来源时间不得未来漂移，水位不得回退；
- 四条来源流的共同水位未最终化前，不得发布可申请现金金额；
- 空批必须推进可验证的扫描水位，迟到事件必须触发重投影或冻结；
- 余额守恒差额必须为零或进入显式非现金/冻结处理；
- 非现金分摊永远不能增加可开票现金；
- 现金累计开票金额不得超过该批次真实支付金额；
- `reserved + issued <= consumed_cash <= verified_cash` 在数据库事务内成立；
- 退款后整批冻结，保持此前确认的保守规则；
- 并发消费、申请、退款和重扫必须有 PostgreSQL 集成测试；
- 乱序到达、跨流延迟、同时间戳不确定顺序和最终化后迟到事件必须有回归测试；
- 任何日志保留/配置/版本门禁失败时，用户端显示暂不可申请，而不是显示估算额度。

## 已冻结的业务决定

1. **历史全部不开放。** 切点前充值、消费和余额不提供自动开票或人工补开入口。
2. **严格事件时间。** 消费发生时，只在当时已经到账的资金中先扣非现金、再扣现金
   FIFO；后来到账的赠送不追溯改写更早现金消费。
3. **未知增量一律非现金。** 无法解释的正余额差额永不产生开票额度；无法解释的负
   差额冻结该用户新增开票额度。
4. **订阅按固定支付金额。** 订阅套餐购买成功并完成外部支付核验后，按实际固定支付
   金额一次性形成可开票额度，不等待套餐消耗；退款仍整单冻结。

这些决定允许新账本从切点开始实施，但不改变“切点前历史不得迁移”的边界。
