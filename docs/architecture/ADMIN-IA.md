## 四、路由映射：原型 hash → 平台真实路由

> `?tab=` 只表示**平台页签**(§2.1),`?sub=` 表示**页内子页签**（§2.2）。两个层级各占一个
> 参数而不是共用 `tab`：平台页里两级同时存在(`/platforms/sub2api?tab=finance&sub=invoices`),
> 共用一个名字就没法同时表达。全局与治理页只有子页签一级，仍然用 `sub`，好让
> 「这是第几级」在任何一页上读法都一样。

迁移硬性要求（交接文档 §8）:

- 未知对象显示 Not Found,**不允许默默回退到第一条样例记录**;
- 筛选、页签和视图进 Router Search Params，保证可分享可恢复;
- 改名必须加 redirect，旧书签不许失效。

## 六、模型保障 / 支付 / 开票：在原型中的确切归属

产品负责人指令：「模型保障，支付，开票系统应该按照 ui 界面全部按平台划分在 sub2api 和 newapi 里面。」
下面是逐字比对结论。

### 6.1 支付 —— ✅ 与指令完全一致

- 基线源里存在独立平台 `{id:"payment",name:"支付",stage:"M3"}`，最终态**用正则整体删除**,
  平台卡计数从「1 / 5」改成「1 / 4」。
- 每个平台获得 `finance` 页签，名称统一为 **「支付与财务」**（基线源里叫「财务中心」）。
- 原型侧栏说明文字改为：`平台（Sub2API 实做, NewAPI/CPA/服务器占位；支付归入各平台）`。
- 原型页面说明逐字:
  > 「本平台的支付与财务：订单、充值、退款、对账与开票都归属当前平台；跨平台页只做汇总。」
- 跨平台汇总保留在治理段 `跨平台财务`。
- 结论：**支付不是平台，是每个平台的页签**；与指令一致，与交接文档 §7.2
  「支付不是单独平台」一致。

### 6.2 开票 —— ✅ 方向一致，但 NewAPI 侧原型未画全

- 原型把开票做成 **Sub2API「支付与财务」下的第 5 个子页签「开票」**,
  并有完整详情页 `#/s2/finance/invoice/<id>`（开票详情）。
- 原型设计注记逐字:
  > 「本平台的钱：订单与充值 + 开票。开票按新结构从独立系统并入这里。」
  > 「支付与开票并入各平台的「支付与财务」。」
- 治理段 `跨平台财务` 另有子页签 **「开票集成」**（跨平台视角）。
- ⚠️ **偏差**:NewAPI 的「支付与财务」在原型里只有 2 个子页签
  (`资金与订单` / `利润核算`),**没有「开票」子页签**。NewAPI 页整体是 M1 阶段的
  薄版本，不是刻意排除开票。
- 结论：归属与指令一致（开票并入各平台支付与财务）;
  **NewAPI 是否补齐 Sub2API 那 5 个子页签（含开票），需产品负责人确认**——
  原型没画，不能替他决定。

### 6.3 模型保障 —— ⚠️ 方向一致，但落点在原型里自相矛盾，需产品负责人拍板

原型里「模型保障」被改名为 **「渠道保障」**，并有一段逐字设计注记明确了降级决定:

> 「模型保障：按你的意见从独立平台降为各 API 平台下的功能。声明 → 探针 → 结论。」

这句话直接支持产品负责人的指令（不再是独立平台）。但最终态的实际落点有 **4 处，且互相不一致**:

| # | 位置 | 形态 | 侧栏/页签可见? |
|---|---|---|---|
| 1 | `#/s2/model` | 完整页「Sub2API · 渠道保障」，3 子页签：保障概览 / 检测任务 / 历史记录 | ❌ **不可见** |
| 2 | CPA 页签 `model` | 「渠道保障」带 M1.5 徽标 | ✅ 可见（但 CPA 是占位平台，点开是占位页） |
| 3 | 渠道详情页 | 卡片「渠道保障记录」+「可用模型：已验证 N / 已配置 M」状态 | ✅ 可见 |
| 4 | `gov/ops` 子页签 | 「模型质量保障」（治理段 运行保障 之下） | ✅ 可见 |

**矛盾点**：最终态在 Sub2API 与 NewAPI 的页签数组里，把
`["upstream","渠道管理"],["model","渠道保障","M1.5"]` 整体替换成了
`["upstream","渠道管理"],["suppliers","上游管理"]` ——
**「渠道保障」页签被「上游管理」顶掉了**。但页面 `V["s2/model"]` 与路由分支
`iid==="model"` 都还在，所以 `#/s2/model` 仍能打开，只是**导航里进不去**。
这是原型自身的孤儿路由，不是有意的隐藏设计。

**如实结论**:

- 「模型保障不再是独立平台」——原型明确支持，与指令一致，可以直接执行。
- 「模型保障应出现在 Sub2API 和 NewAPI 里面」——**原型的导航里现在看不到它**。
  按「以 UI 界面为准严格对齐」的字面要求，Sub2API/NewAPI 不该有这个页签;
  按产品负责人指令的字面要求，应该有。当时列出三个选项未硬编:
  - **A** 恢复「渠道保障」为 Sub2API/NewAPI 的第 9 个页签（原型页面已画好，直接接上）;
  - **B** 维持原型现状：保障只作为渠道详情页的卡片 + 治理段「运行保障 / 模型质量保障」汇总,
    Sub2API/NewAPI 不设独立页签;
  - **C** 折中：平台内不设页签，但「渠道管理」列表补「保障状态」列并可下钻到 `#/s2/model`。
- **✅ 2026-08-28 产品负责人裁定：取 A**（理由与落点见 §8.1）。§2.1 的 Sub2API/NewAPI
  页签表已按此定稿为 9 格，`/platforms/model-assurance` 旧路径 redirect 到
  `/platforms/sub2api?tab=model`。
- 无论选哪个，治理段 `运行保障` 下的「模型质量保障」子页签都保留（跨平台质量视角）,
  这一格原型是明确画了的。

### 6.4 与 ADR-006 的关系：不冲突，但 v2 的转述要改

v2 本文件写「财务中心 ⬜ M3+开票期 | 跨支付+开票统一视图（ADR-006 刻意保留，**不拆进平台**）」。
核对 ADR-006 原文后确认：**这是对 ADR-006 的过度解读**。

ADR-006 的决策是「后台产品体验统一为『财务中心』，但**底层保持三个领域**
(Payment / Reconciliation / Invoice)」，约束的是**数据领域与真相源不合并**,
不是「UI 只能有一个跨平台页」。ADR-006 的硬规则是:

- 开票资格算法只在开票系统实现，平台不得复制;
- 平台可聚合、展示和发起受控管理 Action;
- 原始支付订单仍以来源系统为真相源;
- 不同来源系统的财务隔离不能被统一看板破坏。

原型的做法（每平台一个「支付与财务」页签 + 治理段一个「跨平台财务」汇总页）
**完全满足**这四条：各平台页只做本平台聚合展示，跨平台统一视图仍然存在,
资格算法与真相源都没被搬走。

结论：**无需修订 ADR-006**；但 v2 那句「不拆进平台」的转述作废，v3 已改写。
落地时仍须守住：平台侧的开票页只展示与发起 Action,**不得实现资格判定逻辑**。

## 七、横切规则（不变）

新鲜度铁律 §9.1；写操作只走 Action；金额整数最小单位+币种、未知币种 fail closed;
凭据永不明文（只显示 CredentialRef / 已配置状态）；Fake 来源全局横幅;
逐页 RequireScope、403 提示缺哪个 scope。

原型额外要求的红线（与上面同向，须一并落地）:

- **全局搜索只导航，不执行写命令**——禁止在搜索里放退款、审批、重试、禁用、删除、发布;
- **请求内容属高敏**：默认脱敏，需 `request.content.read` 明确权限，查看动作进审计
  （记录查看人/时间/原因/request_id），默认禁止导出;
- **上游分组未接入时明确显示「未接入」**，不许隐藏;
- **服务器**：供应商账号与服务器登录凭据分离，购买账号密码、Root 密码、SSH Key 均不得回显;
- **F-B 未完成前**，操作与审批页必须显示门禁，不可伪造执行。
- **联系方式在连接器层打码**，不在 HTTP 层：否则明文会先进平台进程内存、日志
  缓冲、错误包装，再在最后一步被抹掉。解析不出的形状整条判为 `invalid-contact`,
  **从不回退到透传**(XM-0046 的测试抓到过：`姓名 <a@b.com>` 这种带显示名的
  形态若只校验域名，会被打码成 `姓名***@b.com>`，真实姓名原封不动地留在输出里)。
- **横向滚动只发生在表格容器内部**（§11.2）：页面 body 永不横滚。
  DataTableV2 的外壳必须是定位祖先——`sr-only` 是 `position:absolute`,
  没有定位祖先时它会跑出滚动容器、把整页撑宽(XM-0045 在浏览器里实测到:
  1024px 视口下 documentElement 因此宽出 38px)。

### 8.5 第 2 片（XM-0043 运营工作台 + 全局搜索）在原型范围内的三处取舍

1. **全局搜索这一版只索引导航**（页面 / 平台 / 页签 / 子页签），不索引用户、订单、
   渠道、服务器、告警编号等**对象**——那需要后端搜索端点，现在没有。
   于是输入框提示语与面板里的范围说明都照实写，**没有照抄原型的占位文案**
   「搜索用户、订单、渠道、服务器、告警或审计编号」：照抄它就是承诺一件做不到的事,
   人搜「张伟」搜不到，只会以为搜索坏了。面板的形态、键盘契约(↑↓ / Enter / Esc /
   Tab 循环 / `aria-activedescendant` / 焦点回到触发按钮)与匹配规则逐条照原型。
2. **「我的待处理」的筛选条是 7 格（全部 + 6 类），原型画了 6 格**。原型的筛选条漏了
   `待评审变更`，但它的 `XM_WORK_ITEMS` 里有这一类的条目——按原型字面渲染的话,
   点任何一个筛选都会把它藏起来，且没有任何办法单独看它。判定为原型自身的不一致,
   按**数据侧**（有这一类）补齐筛选条。
3. **平台状态矩阵含 CPA**。原型矩阵只画了 Sub2API / NewAPI / 服务器 / 开票系统四行,
   没有 CPA(它是 `todo` 占位平台)。侧栏有四个平台而矩阵少一个，会让人以为
   CPA 不归这套看板管；矩阵按平台目录渲染 4 行 + 原型的「开票系统」行，共 5 行。
   开票系统那一行的入口指向治理段 `/finance?sub=invoicing`，与「开票不是平台」一致。

> 本片能接真数据的格子已接真数据（告警 / 指标 / 注册表 / 审计）;
> 「今日到期」「阻塞」两格与「待审批 / 失败任务 / 财务异常 / 即将到期 / 待评审变更」
> 五类没有查询端点，一律显示为「未接入」并写明什么上线之后才会有内容,
> **不显示 0**——0 会被读成「这一类现在没有问题」。

### 8.6 第 5 片（XM-0048 上游管理 + 渠道管理收窄）在原型范围内的五处取舍

1. **§9.6 要求的字段里有三样后端给不出，页面上说出来而不是留空列**：上游名称、
   联系人、上游分组（含未接入分组）——都要扩登记簿的表结构（XM-0037a 没建）。
   页面顶部一句话把它们归到一起并写明被什么挡着——三个「—」看着像数据没加载完，
   而这是「我们还没接」。显示名退而用 `base_url` 的主机名：那是**能从现有数据
   推出来**的最接近的东西，编一个好听的中文名会骗人。
   「本期消耗 / 毛利」两格与行内那一列**已接** XM-0037d 的
   `GET /api/v1/finance/upstreams/summary`（见第 5 条）；「上游总余额与可用天数」
   那个端点也给得出，但它属于另一格的内容，本片没有画。
2. **成本口径按 `access_method` 三分，不照 `metered` 二分**。`metered` 是布尔,
   而设计稿 §2.0 的口径有三套：计量型（实扣 ÷ 倍率）、订阅型（批次摊销）、
   官方 API（v1 待定）。照布尔二分会把官方 API 显示成「订阅摊销」，等于告诉运营
   「这条的成本从订阅批次摊出来」，而它根本没有批次。分工是：**要不要按倍率算**
   问后端(`metered`),**这一格该说什么**看 `access_method`。
3. **登记簿是跨平台的一张表，平台页只显示归属本平台的 + 未配对的**。
   `platform_id` 为空的账号在**两个平台页上都显示**并标「未配对」：按平台过滤掉
   它们，会让一个漏配归属的账号从所有页面上同时消失，而它的成本仍在发生
   （§12 惯例：未接入不许隐藏）。
4. **渠道管理的三列留列不留数——原因不是「端点没上线」，而是 id 对不上**。
   XM-0037d 的 `GET /api/v1/finance/channels/summary` 在本片实施期间已合入,
   但它**一行 = 一个上游账号**（后端 §8.5：两个汇总端点同粒度），而渠道管理表
   一行 = 被管平台自己的一条渠道。两边的 id 互不认识：按 id join 不会报错,
   只会一条都匹配不上，毛利列全空还看着像「后端没数据」。缺的是
   「平台渠道 ↔ 上游账号」的对应关系（登记簿今天只有「上游令牌 ↔ 我方账号」,
   那是另一个维度）。所以三列的列位与数据钩子留好（`lib/channelEconomics.ts`),
   显示「未接入」并在页面上写明真实原因。
   §9.5 还要求的「来源优先显示上游名称」与「可用模型 已验证/已配置 + 前两项 + N」
   同源同因，一并等那层对应关系，不先画空列冒充已接。
5. **上游管理这一侧反而可以直接 join**：两个汇总端点与登记簿的行 id 都是
   `finance.upstream_account` 的主键。所以「本期我方消耗 / 本期整体毛利」两格与
   行内的「本期消耗 / 毛利」列**接的是真数据**。合计遵守两条:
   币种或标度不一致时不给合计（把不同币种的最小单位加起来是纯粹的错数,
   而它看起来完全正常）；只覆盖了一部分账号时标「覆盖不全」并写明几分之几
   （宪法 12 条：覆盖率是金额可解释的前提）。观测时刻取窗口里**最旧**的那个——
   取最新会让整格看起来比实际更新（§9.1）。

### 8.7 概览页逐格映射（XM-0051）

「格 → 数据源 → 状态」。**布局对齐优先，数字诚实第二铁律不变**：
原型有格而平台无数据源的，按原型位置摆出卡片并显示「未接入」+ 一句话说明
数据源属于哪条线，绝不显示 0。

**Sub2API 概览（原型 `V["s2/overview"]`）**

| 格 | 数据源 | 状态 |
|---|---|---|
| 今日调用量 | 无 | 未接入 —— 调用量归 XM-0039 reqlog 只读网关，今天只有逐条请求记录，没有按业务日聚合的指标 |
| 成功率（24h） | 无 | 未接入 —— Sub2API 侧没有成功率指标；NewAPI 的逐渠道错误率是另一个平台、另一个口径，不顶替 |
| 今日充值 | `sub2api.revenue.daily` | ✅ 已接。契约口径是**当天支付订单 `pay_amount` 累加（毛额、不扣退款）**，正是原型说的「充值」；指标注册表里它叫「日收入」，那个名字与 §9.8「用户充值不是当期收入」冲突，页面按契约口径叫充值并写明 |
| 今日成本 | `sub2api.cost.daily` | ✅ 已接。**Sub2API 自己面板的口径**，与今日充值同一份快照 |
| 需要处理的事 | 活跃告警（按 `source_metric_key` 的平台前缀过滤） | ✅ 已接。只收严重/注意两档（info 不进），最多摆 4 条并报出还剩几条 |
| 上游健康 · 上游渠道 | `sub2api.channels.balance` 的 `token_valid` | ✅ 已接。`token_valid` 缺失**算分母不算分子**——状态未知不等于可用 |
| 上游健康 · 订阅账号 | 成本登记簿的订阅型账号 | 🔨 部分。只报启用/停用；原型画的「冷却」「疑似封禁」登记簿没有，要上游账号健康探针（M1.5），不拿 disabled 冒充 |
| 上游健康 · 连接状态 | 指标 source 是否演示实例（`lib/demoData` 同一判据） | ✅ 已接 |
| 近 7 日调用量 | 无 | 未接入 —— 同「今日调用量」。已接的充值/成本七天趋势在两张卡的迷你折线里 |
| 样例数据提示条 | 同上判据 | ✅ 已接，**判得出来才挂**：原型把它写死是因为整站都是样例，真实产品里一条永远在的警告等于没有警告 |

**NewAPI 概览（原型 `V["newapi/overview"]`，结构与 Sub2API 不同）**

| 格 | 数据源 | 状态 |
|---|---|---|
| 用户总数 | `newapi.users.total` | ✅ 已接（含今日活跃） |
| 今日请求量 / 成功率（24h） / 今日订阅 | 无 / 无 / `newapi.subscription.daily` 未观测 | 未接入，各写明原因 |
| 渠道健康 | `newapi.channels.status` | ✅ 已接（渠道 / 类型 / 错误率 / 启停）。原型这张表还有上游、分组、成功率三列：前两列要「平台渠道 ↔ 上游账号」的对应关系（同 §8.6 第 4 条），成功率没有数据源，都不画空列 |
| 近 7 日请求量 | 无 | 未接入 |

**原型没有的格去了哪**（逐条处置，页面底部也写了一句）

| 原有的卡 | 处置 |
|---|---|
| `sub2api.users.total` / `sub2api.users.balance` | 移出概览。它们在「用户管理」页顶部，同一份指标、口径不变 |
| `sub2api.channels.balance` | 不再单独成卡，**并入**「上游健康 · 上游渠道 x / y 可用」；明细在「渠道管理」 |
| 成本三卡 + 贡献利润（XM-0037d） | 保留，单独一行并标题「成本台账口径」。**不与「今日成本」并成一格**：前者是平台自建的成本核算（按上游账号与倍率算），后者是 Sub2API 自己面板报的数，口径不同、不该相减——并成一格才是真正会骗人的做法 |

**一处顺带修的既有缺陷**：`overview` 与 `suppliers` 一样是「一个 `tab.value`
两种语义」的格。概览那个 `case` 原先无条件接管，把 UI 第 6 片给服务器画的
概览蓝图（`blueprints/server.ts`）悄悄换成了一屏通用指标卡。现在按平台分流，
不匹配时落回蓝图兜底，回归用例断言的是**面板内容**而不是页签按钮。

## 十、v2 历史（存档）

v2 是「平台优先的三段式」，统一 6~7 页签模板，平台清单含开票系统/支付/模型保障三个独立条目。

v2 的「一、三段式总树」与「三、v1→v2 迁移映射」由本文件 §一 与 §五 取代。
