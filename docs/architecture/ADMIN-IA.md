## 三、详情路由与深链（原型形态）

原型对「主对象」一律用**完整详情页**，不用右侧抽屉(快照 RECOVERY.md 明确写
「No right-side detail drawers」)。详情页顶部是返回链接(`back()`)。

> **例外：卡片管理（2026-09-05，产品负责人裁定）。**
>
> 卡片页改成左右分栏（左清单、右选中卡详情），**显式推翻本节对这一页的
> 约束**。理由是这一页对标的是 Infini 后台，而产品负责人每天在用那个界面；
> 两边形态一致就不必来回适应，选卡时人认的是卡名而不是卡号，同屏能扫清单
> 又能看详情。这不是实现期的便宜行事，是拿一条明写的规范换一处具体的
> 使用效率，记在这里以便日后有人质疑时能看到当时的取舍。
>
> **本节真正在乎的实质仍然保住了**：选中哪张卡写进路由
> （`/cards/:account/:cardId`），详情依然可链接、可刷新、可发给同事。
> 被推翻的是视觉形态，不是可链接性——Infini 自己的右栏选中态只活在内存里，
> 刷新就回到第一张，我们这版比它多这一层。
>
> 例外只限卡片管理一页。其它主对象继续走完整详情页。

> `?tab=` 只表示**平台页签**(§2.1),`?sub=` 表示**页内子页签**（§2.2）。两个层级各占一个
> 参数而不是共用 `tab`：平台页里两级同时存在(`/platforms/sub2api?tab=finance&sub=invoices`),
> 共用一个名字就没法同时表达。全局与治理页只有子页签一级，仍然用 `sub`，好让
> 「这是第几级」在任何一页上读法都一样。

迁移硬性要求（交接文档 §8）:

- 未知对象显示 Not Found,**不允许默默回退到第一条样例记录**;
- 筛选、页签和视图进 Router Search Params，保证可分享可恢复;
- 改名必须加 redirect，旧书签不许失效。

## 六、模型保障 / 支付 / 开票：在原型中的确切归属

产品负责人指令：「模型保障，支付，开票系统应该按照 ui 界面全部按平台划分在 sub2api 和 newapi 里面。」
下面是逐字比对结论。

### 6.1 支付 —— ✅ 与指令完全一致

- 基线源里存在独立平台 `{id:"payment",name:"支付",stage:"M3"}`，最终态**用正则整体删除**,
  平台卡计数从「1 / 5」改成「1 / 4」。
- 每个平台获得 `finance` 页签，名称统一为 **「支付与财务」**（基线源里叫「财务中心」）。
- 原型侧栏说明文字改为：`平台（Sub2API 实做, NewAPI/CPA/服务器占位；支付归入各平台）`。
- 原型页面说明逐字:
  > 「本平台的支付与财务：订单、充值、退款、对账与开票都归属当前平台；跨平台页只做汇总。」
- 跨平台汇总保留在治理段 `跨平台财务`。
- 结论：**支付不是平台，是每个平台的页签**；与指令一致，与交接文档 §7.2
  「支付不是单独平台」一致。

### 6.2 开票 —— ✅ 方向一致，但 NewAPI 侧原型未画全

- 原型把开票做成 **Sub2API「支付与财务」下的第 5 个子页签「开票」**,
  并有完整详情页 `#/s2/finance/invoice/<id>`（开票详情）。
- 原型设计注记逐字:
  > 「本平台的钱：订单与充值 + 开票。开票按新结构从独立系统并入这里。」
  > 「支付与开票并入各平台的「支付与财务」。」
- 治理段 `跨平台财务` 另有子页签 **「开票集成」**（跨平台视角）。
- ⚠️ **偏差（已由 CR-0005 解决，见下）**:NewAPI 的「支付与财务」在原型里只有
  2 个子页签(`资金与订单` / `利润核算`),**没有「开票」子页签**。NewAPI 页整体
  是 M1 阶段的薄版本，不是刻意排除开票。
- 结论：归属与指令一致（开票并入各平台支付与财务）;
  **NewAPI 是否补齐 Sub2API 那 5 个子页签（含开票），需产品负责人确认**——
  原型没画，不能替他决定。
- **✅ 2026-09-02 产品负责人指令，见 CR-0005**：NewAPI 补齐「开票」子页签。
  第一阶段是嵌入式迁入（`EmbeddedConsoleFrame` 承载开票系统管理端的
  `/embed/admin/newapi`），不是原生列表——原生列表仍要等第二阶段的只读连接器
  与 CR-0002 冻结。§8.2 #2 的「不补开票」裁定到此为止，不再适用；§2.2 的
  `newapi/finance` 子页签表已按此更新为 3 格。

原型里「模型保障」被改名为 **「渠道保障」**，并有一段逐字设计注记明确了降级决定:

> 「模型保障：按你的意见从独立平台降为各 API 平台下的功能。声明 → 探针 → 结论。」

这句话直接支持产品负责人的指令（不再是独立平台）。但最终态的实际落点有 **4 处，且互相不一致**:

| # | 位置 | 形态 | 侧栏/页签可见? |
|---|---|---|---|
| 1 | `#/s2/model` | 完整页「Sub2API · 渠道保障」，3 子页签：保障概览 / 检测任务 / 历史记录 | ❌ **不可见** |

| 3 | 渠道详情页 | 卡片「渠道保障记录」+「可用模型：已验证 N / 已配置 M」状态 | ✅ 可见 |

`["upstream","渠道管理"],["suppliers","上游管理"]` ——

这是原型自身的孤儿路由，不是有意的隐藏设计。

- 「模型保障不再是独立平台」——原型明确支持，与指令一致，可以直接执行。
- 「模型保障应出现在 Sub2API 和 NewAPI 里面」——**原型的导航里现在看不到它**。
  按「以 UI 界面为准严格对齐」的字面要求，Sub2API/NewAPI 不该有这个页签;
  按产品负责人指令的字面要求，应该有。当时列出三个选项未硬编:
  - **A** 恢复「渠道保障」为 Sub2API/NewAPI 的第 9 个页签（原型页面已画好，直接接上）;
  - **B** 维持原型现状：保障只作为渠道详情页的卡片 + 治理段「运行保障 / 模型质量保障」汇总,
    Sub2API/NewAPI 不设独立页签;
  - **C** 折中：平台内不设页签，但「渠道管理」列表补「保障状态」列并可下钻到 `#/s2/model`。
- **✅ 2026-08-28 产品负责人裁定：取 A**（理由与落点见 §8.1）。§2.1 的 Sub2API/NewAPI
  页签表已按此定稿为 9 格，`/platforms/model-assurance` 旧路径 redirect 到
  `/platforms/sub2api?tab=model`。
- 无论选哪个，治理段 `运行保障` 下的「模型质量保障」子页签都保留（跨平台质量视角）,
  这一格原型是明确画了的。

### 6.4 与 ADR-006 的关系：不冲突，但 v2 的转述要改

v2 本文件写「财务中心 ⬜ M3+开票期 | 跨支付+开票统一视图（ADR-006 刻意保留，**不拆进平台**）」。
核对 ADR-006 原文后确认：**这是对 ADR-006 的过度解读**。

ADR-006 的决策是「后台产品体验统一为『财务中心』，但**底层保持三个领域**
(Payment / Reconciliation / Invoice)」，约束的是**数据领域与真相源不合并**,
不是「UI 只能有一个跨平台页」。ADR-006 的硬规则是:

- 开票资格算法只在开票系统实现，平台不得复制;
- 平台可聚合、展示和发起受控管理 Action;
- 原始支付订单仍以来源系统为真相源;
- 不同来源系统的财务隔离不能被统一看板破坏。

原型的做法（每平台一个「支付与财务」页签 + 治理段一个「跨平台财务」汇总页）
**完全满足**这四条：各平台页只做本平台聚合展示，跨平台统一视图仍然存在,
资格算法与真相源都没被搬走。

结论：**无需修订 ADR-006**；但 v2 那句「不拆进平台」的转述作废，v3 已改写。
落地时仍须守住：平台侧的开票页只展示与发起 Action,**不得实现资格判定逻辑**。

- **F-B 未完成前**，操作与审批页必须显示门禁，不可伪造执行。

  缓冲、错误包装，再在最后一步被抹掉。解析不出的形状整条判为 `invalid-contact`,

- **横向滚动只发生在表格容器内部**（§11.2）：页面 body 永不横滚。
  DataTableV2 的外壳必须是定位祖先——`sr-only` 是 `position:absolute`,

### 8.6 第 5 片（XM-0048 上游管理 + 渠道管理收窄）在原型范围内的五处取舍

1. **XM-C003 已补上账号级上游名称、联系人和已接入分组**：三者是
   `finance.upstream_account` 的可空当前元数据，空值在页面明确显示「未接入」，

   归并键；未接入分组发现与真正供应商聚合仍需后续 supplier/group 结构。
2. **成本口径按 `access_method` 三分，不照 `metered` 二分**。`metered` 是布尔,
   而设计稿 §2.0 的口径有三套：计量型（实扣 ÷ 倍率）、订阅型（批次摊销）、
   官方 API（v1 待定）。照布尔二分会把官方 API 显示成「订阅摊销」，等于告诉运营
   「这条的成本从订阅批次摊出来」，而它根本没有批次。分工是：**要不要按倍率算**
   问后端(`metered`),**这一格该说什么**看 `access_method`。
3. **登记簿是跨平台的一张表，平台页只显示归属本平台的 + 未配对的**。

   （§12 惯例：未接入不许隐藏）。
4. **渠道管理的三列留列不留数——原因不是「端点没上线」，而是 id 对不上**。

   但它**一行 = 一个上游账号**（后端 §8.5：两个汇总端点同粒度），而渠道管理表
   一行 = 被管平台自己的一条渠道。两边的 id 互不认识：按 id join 不会报错,
   只会一条都匹配不上，毛利列全空还看着像「后端没数据」。缺的是
   「平台渠道 ↔ 上游账号」的对应关系（登记簿今天只有「上游令牌 ↔ 我方账号」,
   那是另一个维度）。所以三列的列位与数据钩子留好（`lib/channelEconomics.ts`),
   显示「未接入」并在页面上写明真实原因。
   §9.5 还要求的「来源优先显示上游名称」与「可用模型 已验证/已配置 + 前两项 + N」
   同源同因，一并等那层对应关系，不先画空列冒充已接。
5. **上游管理这一侧反而可以直接 join**：两个汇总端点与登记簿的行 id 都是
   `finance.upstream_account` 的主键。所以「本期我方消耗 / 本期整体毛利」两格与
   行内的「本期消耗 / 毛利」列**接的是真数据**。合计遵守两条:
   币种或标度不一致时不给合计（把不同币种的最小单位加起来是纯粹的错数,
   而它看起来完全正常）；只覆盖了一部分账号时标「覆盖不全」并写明几分之几
   （宪法 12 条：覆盖率是金额可解释的前提）。观测时刻取窗口里**最旧**的那个——
   取最新会让整格看起来比实际更新（§9.1）。

#### 07:20 补充裁定的精确实现细节（team-lead 直接发给 XM-CHAN-MERGE0 的规格）

ACCEPTANCE-LOG 里的 07:20 裁定条目是产品负责人裁定的**摘要**；team-lead
随后直接给 XM-CHAN-MERGE0 发了一份更精确的规格（含逐字段 JSON 名），补记于此,
免得只看 ACCEPTANCE-LOG 摘要的人漏掉这些实现细节：

- **`平台 / 类型` 列显示真实供应商名，不是平台徽章**：`row.vendor`（新契约
  字段）优先，取不到就退回登记簿 join 的 `upstream_name`。页面本身已经是
  单平台域（Sub2API 页签 vs NewAPI 页签），再放一个"Sub2API"/"NewAPI" 徽章
  是重复信息；供应商名才是这一格真正在区分的东西。
- **`倍率 / 上游倍率` 与 `平台 / 类型` 的"类型"部分，是"新字段优先、退回
  已有真实数据"，不是从头到尾未接入**：`row.rateMultiplier`/
  `row.upstreamMultiplier` 优先于登记簿 join 的 `group_rate`/`recharge_ratio`;
  `row.kind` 优先于 `accountRowType`（从 access_method 派生）。今天两个新
  字段都是 null，所以显示的仍是登记簿 join 的真实值，不是未接入——这两处与
  下面 8 个纯新增字段的诚实策略不同，是"有真数据先用，更权威的来源来了自动
  切换"，不是无中生有也不是假装没有数据。
- **`状态` 列没有接 `row.status`**：那是 chanfields 还没定形的枚举，贸然
  映射进既有的健康/需关注徽章体系等于猜它的取值范围，违反宪法 12 条。
  `PlatformChannelRow` 类型上已经留了 `status: string | null` 字段位置，
  但渲染逻辑维持现状（绑定 + 观测新鲜度），这是记录在案的刻意取舍。
- **JSON 字段名**（`PlatformChannelFieldsExtension`，`api/platformChannels.ts`,
  全部可空，全部按这些名字解析）：`kind`("subscription"|"upstream")、
  `vendor`、`status`、`capacity`{used,limit}、`scheduling`{enabled,priority}、
  `today`{requests,success_rate,cost_minor,currency,scale}、`usage_window`
  {used_ratio,resets_at}、`proxy`、`rate_multiplier`、`upstream_multiplier`、
  `last_used_at`、`created_at`、`expires_at`。`id`/`name` 没有对应新增字段——
  `channelRef.externalChannelId`/`name` 已经是稳定的真实数据源，加一个同义的
  新字段只会制造两个真相源，没有价值。
- **调度列即使字段到位也保持只读**：渲染一个 `role="switch"
  aria-disabled="true"` 的禁用态开关（ui-primitives today 没有现成 Toggle
  组件，这里用既有 token 化工具类画一个纯展示用的假开关，不是新增可复用
  组件）+ 优先级数字，固定 tooltip 文案「调度开关待 XM-SCHED0 Action」。
- **`用量窗口` 按类型分叉**：类型是"上游渠道"时这一格是**不适用**（不是
  未接入——上游渠道本来就没有用量窗口这个概念）；类型是"订阅账号"或还
  "未映射"时，字段非 null 显示真值，null 显示未接入。
- **筛选**：`平台 / 来源`（按真实供应商名动态生成选项 + 未映射，不是原型
  的假供应商列表；回到了 04:40 那一版最初的做法）、`类型`（订阅账号/上游
  渠道/未映射——多出的"未映射"选项是为了让未绑定的行有筛选入口，不然会
  漏筛）、`状态`（健康/需关注）。
- **视图**：全部 / 订阅账号 / 上游渠道 / 需关注（四个，逐字照 team-lead 的
  规格；"未映射"不再单独占一个预置视图，但仍是"类型"筛选下拉里的一个选项）。
- **类型加到 `PlatformChannelFieldsExtension` 上是为了让 chanfields 交付之后
  不用再改前端代码**：字段一旦从 null 变成有值，`ManagedChannelTable.tsx`
  与 `ChannelDetailPage.tsx` 的渲染逻辑已经在读这些字段，会自动显示真值。
