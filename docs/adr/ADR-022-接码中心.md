# ADR-022 接码中心

## 状态

Accepted（2026-09-06，产品负责人口头决策，本 ADR 记录）

## 背景

XM-SMS0/SMS1 把 62-US 与 Hero-SMS 两家的全部官方接口接进了平台，但形状仍是
「两家供应商各自的功能堆在一页上」：

- 供应商名字写死在 8 处（5 张表的 CHECK、`AllProviders`、`SupportsAction`、
  凭据引用、两个适配器、替身、页面标签），接第三家要改迁移加七处代码；
- 页面以供应商为中心，人得先想「用哪家」再想「要什么号」，与日常工作相反；
- 号码状态是上游原话（Hero 的 `1`、62 的 `active`），没有统一含义；
- 成本没有台账，单价散在资源 / 订单 / 邮箱三张表里；
- 所有 Action 只允许 HUMAN，别的模块和外部用户都进不来。

产品负责人 2026-09-06 的要求：改名「接码中心」；为后续不同上游接入做准备；
管理后台更好用；包含成本计算（后期纳入跨平台财务中心）；预留接口给其他功能调用
或建设用户前端转售号码。

## 决策

1. **定位**：接码中心与卡片并列，是「平台自持的一次性资源」中心。供应商是实现细节。
2. **多上游**：引入供应商注册表 `ProviderSpec{ID, 标签, 能力集, 凭据引用, 构造}`。
   能力集（purchase / lifecycle / rent / email / catalog / history / balance…）取代按
   名字的 switch；数据库不再对 provider 做 CHECK。**接一家新供应商 = 一个 Go 包 +
   注册表一行，不改迁移。**
3. **要号流程**：以「服务 + 国家」为中心；**默认由系统按路由规则自动选供应商**，
   人只在想指定时才选。路由规则（优先级、回落、单价上限）在管理后台配，走 Action。
4. **统一状态**：待收码 / 已收码 / 已完成 / 已取消 / 已过期，上游原始状态保留一列。
5. **成本**：成本事件台账 `sms.cost_event` 由七态台账在成功那一刻写入；余额快照表
   与之对账；统计**分币种不折算**（与卡片同口径）；这张事实表按「日 × 供应商 ×
   币种」供跨平台财务汇总。
6. **对外接口**：**先内部使用**，具体消费者未定，但**先建立接入规范**（机器身份、
   API Key、幂等申请、配额与花费上限、码到达回调）。
7. **转售**：**预充值扣费**模式，建在现有平台用户 + 支付模块之上；售价 = 成本 ×
   加价规则；销售写 `sms.sale`，利润按币种分。
8. **通知**：平台通知规范由另一条线制定中。接码中心的告警条件（余额低、unknown
   待核对、租用到期）先落成**内部事件与页面提示**；外发（企业微信 / Webhook）
   等规范定稿后适配，**不自建第二套外发通道**。

## 理由

- 注册表 + 能力集是唯一能把「接第三家」从八处改动压到一处的形状；页面按能力
  渲染而不是按名字，也就不会出现「62 出现在租用页然后报不支持」。
- 以要号为中心是因为日常问题是「我要一个 Google 的美国号」，不是「我要用 Hero」。
  自动路由把供应商的差异（价格、库存、成功率）变成规则而不是每次的人工判断。
- 成本必须是事件台账而不是从资源表反推：延长、重激活、退款都不改资源单价，
  只有事件能记下每一分钱的来龙去脉；余额对账是发现「上游多扣了」的唯一方法。
- 先定接入规范再等消费者：规范决定幂等键、配额、回调这些一旦有消费者就改不动的
  东西。
- 预充值与现有支付模块贴合，且把「客户欠费」这一类风险挡在门外。

## 边界与后果

- 通知外发不在本 ADR 范围；与通知规范的接口是「事件 + 严重度 + 建议动作」。
- 转售门户（阶段 4）依赖平台用户 / 支付模块的成熟度，本 ADR 只定模式与数据形状。
- 去掉 provider 的 CHECK 后，一个拼错的 provider 名会进表：由注册表在写路径校验
  兜底（写路径全部经 Action → Service → 注册表）。

## 替代方案

- 每家供应商一个独立页面、独立表：接入最快，但成本无法汇总、路由无从谈起，
  第三家时就得推倒。
- 立即做转售门户：收入侧的数据不在平台，成本台账没有就没法算利润，顺序错。

## 重评条件

- 出现第三家供应商时验证「一个包 + 一行」是否成立；
- 通知规范定稿后重看第 8 条；
- 首个内部消费者接入时重看接入规范的幂等与配额条款。
