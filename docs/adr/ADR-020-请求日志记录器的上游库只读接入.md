# ADR-020：请求日志记录器的上游库只读接入

| 项 | 值 |
|---|---|

| 日期 | 2026-09-03 |

## 背景

请求日志记录器（`cmd/reqlog-recorder`，宿主机 systemd 服务，`User=root` 运行，平台自有代码）为了把请求记录关联到用户，需要一份 token 前缀→用户身份的映射。它的 `refreshTokenMap`（`cmd/reqlog-recorder/tokenmap.go:43`）定期对 NewAPI、Sub2API 两个上游各执行一次 `docker exec ... psql`，把只读查询结果写入 `tokenmap.json`（写盘见 `tokenmap.go:75`；路径/权限见 `config.go` 的 `TokenMapPath`/`DirPerm`/`FilePerm`/`GroupID`）。这条链路是从桌面端原型收编（`XM-REQLOG-MERGE`）而来的既有生产事实，收编时明确原样保留、未重新设计（`XM-REQLOG-MERGE.md` 风险 #1、`REQLOG-RECORDER.md`"已知限制"）。

它不经过 Connector 抽象，也不使用 `SecretProvider`/`CredentialRef`（ADR-014），因此不受 ADR-018 四道只读闸约束——那四道闸的适用范围明确是"平台对 NewAPI/Sub2API 建立独立只读账号"这条经 Connector 建立的连接，`docker exec` 不是这样一条连接，两条 ADR 都没有预见它。

CR-0008 要求这条链路多导出一列 `u.id`（上游稳定用户 ID），把它从"仅供人工排查的用户名映射"升级为"承载稳定身份关联、驱动产品功能（reqlog 用户过滤/`UserRef`）的数据源"。`REQLOG_USERREF_APPROVAL` 的宽批准分支明确要求"先立 ADR/Change Request"才能做这次信任等级升级；产品负责人批准时追加硬约束：**不得改动 Sub2API 与 NewAPI 源码**，只允许经既有只读 API 或只读数据库角色读取。本 ADR 是这条硬约束下的前置 ADR。

## 决策

### 一、直连路径作为有边界的例外被接受，不是 Connector

`cmd/reqlog-recorder` 对 NewAPI/Sub2API 数据库的直连导出被接受为独立于 Connector 体系的、有明确边界的例外，不追认为 Connector，也不套用 ADR-018 四道闸的字面形式——那四道闸是为经 Connector 建立的连接设计的运行期机制，`docker exec` 这条通道拿不到同等的运行期强制力。以下不变量替代四道闸，作为例外的边界，任何扩大都需要修订本 ADR：

1. **语句面只读，表/列封闭列举**：两条导出 SQL 逐字为 `SELECT`，只涉及：
   - NewAPI（`tokenmap.go:48`）：`tokens`（列 `key`、`user_id`）、`users`（列 `id`、`username`），经 `users.id = tokens.user_id` 关联；
   - Sub2API（`tokenmap.go:57`）：`api_keys`（列 `key`、`user_id`）、`users`（列 `id`、`username`、`email`），经 `users.id = api_keys.user_id` 关联；
   - CR-0008 的改动是在两条查询已有的 `JOIN` 上各多 `SELECT` 一列已关联到的 `users.id`，不新增表、不新增 `JOIN`、不新增语句（CR-0008"变更范围"第 1 条）。
2. **连接主体现状如实记录，不是四道闸的等价物**：今天这条通道以 `docker exec` 进两个具名容器执行 `psql`，NewAPI 侧显式声明 `-U root`（`tokenmap.go:48`），Sub2API 侧使用该容器已配置的 `$POSTGRES_USER`（`tokenmap.go:57`）——**都不是专用只读数据库角色**，"只读"这一属性今天完全由查询文本承载，不是由数据库权限承载，这与 ADR-018 四道闸（尤其闸 2/3 的运行期强制只读与服务端复核）有实质差距。本 ADR 如实记录这一差距，不把它描述成已经具备专用只读角色。若 NewAPI/Sub2API 未来提供专用只读数据库角色，导出连接应改用该角色（CR-0008"兼容性/安全"一节已作同样表述）；角色切换属于运维配置变更，不强制同 PR 代码改动，但要求切换后回本 ADR 补记"连接主体现状"。
3. **凭据落地现状如实记录**：这条通道不经过 `SecretProvider`/`CredentialRef`，没有独立的凭据文件——"凭据"事实上是宿主机 `root` 身份本身（`deploy/reqlog/reqlog-recorder.service` 的 `User=root`）加上该身份对 Docker socket 的访问权；数据库侧认证在容器内部完成（容器已配置好的本地信任/环境变量），平台侧管理不到、也看不到这一层，`docs/runbooks/REQLOG-RECORDER.md` 通篇未记录任何独立凭据文件。本 ADR 不要求为这条例外新建一份平行的凭据管理机制，但要求 CR-0008 实现切片在该 runbook 补一句现状说明，供后续审计者不必重新读源码确认。
4. **无网络暴露**：`docker exec` 只能从宿主机本机发起，导出结果只落盘为本机文件（`tokenmap.json`/CR-0008 新增的 `tokenmap.v2.json`），不开放任何网络端口；只读文件经既有只读绑定挂载（`0750`/`0640` + GID 10001）供容器化 `platform-api` 消费，不是新增的暴露面。

### 二、机械防护：CR-0008 实现必须新增的守卫测试

不变量 1（语句面只读）不能只靠人工审阅维持。CR-0008 的实现切片必须在 `cmd/reqlog-recorder` 新增一条测试，对 `refreshTokenMap` 里的两条 SQL 字符串做静态断言：不含 `insert`/`update`/`delete`/`drop`/`alter`/`truncate`/`grant` 等写关键字（CR-0008 验收标准第 4 条已要求这一半），并且只引用本 ADR"决策·一·1"列出的表名——后一半是本 ADR 在 CR-0008 既有断言上追加的要求，防止未来有人在同一函数里顺手多拼一条查询新表却没人发现。这条测试的精神与 `internal/platform/pgreadonly`（`pgreadonly.go` 的 `AssertSelectOnly`/`ErrWriteAttempt`，ADR-018 四道闸在数据库通道上的共享实现）一致，但机制不同：`pgreadonly` 在运行期拦截真实连接上的每条查询，这里的两条 SQL 是编译期常量字符串，测试只需要对源码里的字符串字面量做静态断言，不需要真实数据库连接。

### 三、退出路径

`connectors/platformusers` 的 Connector 化身份读取（platform-user-read-v2，NewAPI/Sub2API 的 real reader 已分别获 `NEWAPI_REAL_APPROVAL`/`SUB2_REAL_APPROVAL` 批准，2026-09-03）已在契约里预留 `User.TokenPrefix`（`connectors/platformusers/contract.go:365-367`，"该用户某个 API Key 的前缀，供与请求列表对账"）。当这条 Connector 路径的 real reader 在两个上游都能稳定填出 `TokenPrefix`（今天至少一侧的 real 实现仍将其留空，见 `connectors/platformusers/upstream.go:138`）时，`tokenmap` 导出应迁移为改查这个 Connector，本例外随之退役。触发条件与负责人：验收线在双侧 `TokenPrefix` 就绪时提出迁移变更单，产品负责人批准迁移时机；不设固定日期，因为依赖上游只读 API/角色的可用性，不由本 ADR 单方面承诺。

## 理由

这条通道是收编前就已经在生产运行的既有事实，不是本 ADR 新建的能力；真正改变的是它被信任来承载的数据等级（从"人工排查用的用户名"升级到"驱动产品功能的稳定 ID"）。用不变量加机械测试的组合，把这条无法立刻纳入 Connector 抽象的例外钉死边界、可审计、可在条件满足后退役，好过两个更差的选择：放着不管（"升级信任等级"这件事本身不会被任何文档承认），或者假装它已经符合 ADR-018 四道闸（不成立，闸 2/3 是运行期机制，这条通道给不出同等强制力）。

## 边界与后果

- 正面：CR-0008 的实现有了明确、可验证的合入前提，不再是"先斩后奏"或无限期搁置；`REQLOG_USERREF_APPROVAL` 宽批准分支的前置条件落地有了对应文档。
- 负面/风险：本 ADR 承认（不是掩盖）当前连接主体不是专用只读角色这一差距；机械测试能挡住"新增语句/新增表"，但挡不住"给已枚举的列换一种更敏感的用法"这类误用，仍依赖代码审阅。
- 宪法第 5 条"不直写第三方原始表"由本例外的语句面只读不变量满足（只读不等于零风险，但满足"不写"这条字面要求）；宪法第 7 条"凭据只经 CredentialRef"对这条通道是**不适用**而非**满足**——这是本 ADR 明确记录的一处既有缺口，不是本 ADR 制造的新缺口，也不在本 ADR 范围内被关闭。

## 替代方案

1. **现在就把导出迁进 Connector**：否决——`connectors/platformusers` 的 real reader 今天还没有两侧都可用的 `TokenPrefix`，`NEWAPI_REAL_APPROVAL`/`SUB2_REAL_APPROVAL` 的批准范围也不含这一读取面，现在做会绕开审批边界。
2. **不再关联身份，只保留 Username**：否决——这正是 `REQLOG_USERREF_APPROVAL` 的"窄批准"分支，会让 Task 8（reqlog 稳定 UserRef 面板）事实上不可行；产品负责人已选择"宽批准，另需 ADR/CR"，本 ADR 是那个前置条件。
3. **把上游表整份同步/复制进平台数据库**：否决——既违反宪法第 5 条"不拥有第三方业务真相"，也把两份数据的一致性问题从"一次只读查询"变成"一条同步管道"，复杂度和风险都更高。

## 重评条件

- 若 NewAPI/Sub2API 任一方提供专用只读数据库角色，导出连接切换后回本 ADR 补记"决策·一·2"；
- `connectors/platformusers` real reader 的 `TokenPrefix` 在两个上游都稳定可用后，评估退役本例外（见"决策·三"）；
- 若这条通道被要求扩大读取范围（新表、新列、新上游），必须先修订本 ADR，不得直接在 `tokenmap.go` 加语句。
