# ADR-019：渠道主动探测通道（检测任务）

| 项 | 值 |
|---|---|
| 状态 | 提议（待产品负责人拍板；见文末"待拍板问题"） |
| 日期 | 2026-09-03 |
| 来源 | XM-ASSURE0 交接文档 follow_ups 的设计笔记（`docs/handoffs/slices/XM-ASSURE0-passive-assurance.md`）；ADMIN-IA `s2/model`/`newapi/model` 页面"检测任务"子页签（`docs/architecture/ADMIN-IA.md` §六.3、§8.1 裁定 #1） |

## 背景

XM-ASSURE0 交付了"渠道保障"页签的被动指标（保障概览 + 历史记录），数据完全来自
请求审计索引（reqlog），不发起任何新请求。"检测任务"子页签被明确排除在外，原型
文案是"支持不定时抽检，也保证最低检测频率"——这需要平台**主动**发起真实请求去
问模型"你还好吗"，与被动统计是两种完全不同性质的动作。ASSURE0 交接文档的
follow_ups 已经点出了尚未解决的定性问题：

> 探测本身就是要"发一个真实请求去看模型是否正常响应"，这与 ADR-018 的"只读闸"
> 精神（平台不该代表用户发起业务请求）存在张力，需要单独判断这属于"平台自身的
> 健康探测"（更像 `ops` 域的探针）还是"代表用户的业务调用"（那就该完全避免）。

本 ADR 就是这个"先定性"的产物。

## 决策

### 一、探测是什么，不是什么

探测（Probe）是平台向**被管平台自己面向其付费用户暴露的 OpenAI 兼容推理端点**
（如 Sub2API/NewAPI 各自的 `/v1/chat/completions` 或等价路径）发出的、使用一个
**专用探测 API Key**（注册为独立 `CredentialRef`，与 ADR-018 的只读 admin 凭据完全
分离）的真实小请求，目的是验证"这条渠道 · 这个模型现在能不能正常应答"。

明确边界：

- **探测从不直接联系上游厂商**（Anthropic/OpenAI/Azure 等）——探测目标永远是
  Sub2API/NewAPI 自己的产品接口，就像它们自己的付费用户会打的那个接口一样；
  上游是否健康，由被管平台自己的路由/重试/降级逻辑决定，探测只看"被管平台给
  我的答案对不对"。
- **探测从不触碰 admin API**，ADR-018 的四道只读闸（拒绝可写连接配置、强制
  read-only 事务、复核只读设置、Connector 包内无写路径）继续原样把守只读通道，
  本 ADR 不修改、不放宽它们一个字。探测走的是第三条、全新的出站通道。
- **探测不是"代表用户发起业务请求"**：探测流量归属于平台自己持有的专用账号，
  从不出现在任何真实用户的请求路径里，不消耗任何用户的额度或余额，其结果只
  写入平台自己的检测记录表——宪法第 5 条"平台不参与用户实时请求路径"约束的是
  "替用户做业务"，探测是平台对自己管理对象的自检，性质更接近
  `internal/platform/jobs/connector_probe.go` 已经在做的"周期性问 Version()/
  Health()"，只是这次问的是模型层而不是连接层，因此天然要花真钱、要有预算。

### 二、与 ADR-004/ADR-018 的关系

ADR-004 的读/写通道优先级管的是"平台如何得知被管平台自己业务数据的事实"和
"平台如何变更被管平台自己的配置"——探测两者都不是：它不读被管平台的业务表，
也不改被管平台的任何配置，它只是**把被管平台当成它自己产品的一个使用者去访问
它自己已经公开的产品接口**。ADR-004/ADR-018 在设计时没有预见这第三种通道，本
ADR 是它的权威来源：

- 新增能力命名空间 `sub2api.probe.chat_completion` / `newapi.probe.chat_completion`
  （非 `ReadCapabilities` 的一员，不进 `connectors/sub2api|newapi` 现有的
  `ReadClient` 接口——那个接口的契约注释明确写着"只有读方法"，探测是另一个
  独立的、允许发出真实推理请求的客户端形状，实现随 XM-ASSURE1-core 落地）；
- 探测凭据是**新的一个字段**，不复用 `core.connector_config.credential_ref`
  （那个字段是 ADR-018 只读 admin 账号的引用）；
- 探测请求的目标主机仍必须落在该平台 `core.connector_config.target_allowlist`
  内（ADR-004 铁律：任何出站目标都要过白名单，探测不例外，即使它访问的是
  admin API 之外的路径）。

### 三、风险等级：`assurance.probe.run@1` 定为 L1，不是 L2

`assurance.probe.declare@1`（声明/编辑探测任务）与 `assurance.probe.cancel@1`
（撤销声明）是纯配置写操作，与 `finance.upstream_account.set@1`、
`connector.config.set@1` 同类，定为 **L1** 没有争议。

真正需要拍板的是 `assurance.probe.run@1`——这个 Action 会让一个 River 任务真的
发出计费的出站请求。凭直觉，"发真实出站流量、花真钱"很容易被归到 L2（"批量
配置、启停低风险资源"）。本 ADR **不采用这个直觉**，定为 **L1**，理由如下：

1. **L2+ 在 Foundation-A 下不是"需要多一道审批"，而是内核硬拒绝，完全不可
   执行。** `internal/platform/action/risk.go` 的 `RequiresAdvancedControls()`
   对 L2/L3/L4 一律返回 true；`internal/platform/action/kernel.go:156-160` 对
   `RequiresAdvancedControls()==true` 的 Action 直接返回
   `CodeAdvancedControlsRequired`，不落一次真正的执行。翻遍
   `contracts/actions/*.json`，**当前可执行的 Action 无一例外是 L0 或 L1**；
   仓库里仅有的三个 L2/L3 声明（`registry.connector.create`、
   `registry.connection.create`、`registry.connection.set_status`）都在
   `docs/modules/action/PERMISSIONS.md` 里被明确标注"❌ 需 Foundation-B"——
   它们是**冻结好等着 Foundation-B 接线的空壳**，不是"能跑但要审批"。如果
   `probe.run` 定为 L2，XM-ASSURE1 连 fake 模式的验证都无法执行，必须等
   XM-0030（Action Advanced Controls，见
   `docs/superpowers/plans/2026-08-27-xm-0030-action-advanced-controls-design.md`，
   目前状态是"设计稿，待产品负责人拍板"，落地时间不可控）——这与"先 fake
   模式验证、真实模式另等负责人开关"的既定路线直接冲突，也不是
   ASSURE0 follow_ups 期待的"下一片直接起步"。
2. **单次探测的实际风险形状更接近 L1 的例子，而不是 L2 的例子。** ADR-003
   的等级表里，L1 是"修改低风险平台配置、确认普通告警"，L2 是"批量配置、
   启停低风险资源"。一次 `probe.run` 只对**一个平台 × 一次固定极小 Prompt ×
   声明好的目标渠道/模型清单**发起请求，不批量、不改任何用户可见状态，
   探测结果只是一行新记录；出错的最坏后果是浪费掉一次探测的固定 token 上限，
   不是"启停一批资源"那种量级和不可逆性。
3. **L1 允许的"按需幂等"控制手段，恰好是本 ADR 用来兜底真实风险的工具**：
   强制的 Kill Switch 检查（业务规则，不依赖 Action 风险分级机制）、每次探测
   固定的 `max_tokens` 硬上限、每平台每日探测预算硬顶、同平台同时只允许一个
   在跑的探测（并发闸，见规格文档）——这套工具与现有 `connector.config.set@1`
   （L1，切真实模式前的把关）、`internal/platform/jobs/connector_probe.go`
   （周期性连接健康探测，同样发真实出站请求但完全不经过 Action）解决的是
   同一类"小而受控的出站动作"问题，用的是同一套纪律。

**遗留给 Foundation-B 之后重新评估的问题**（见文末"待拍板问题"）：XM-0030
落地后，`probe.run` 是否应该改判 L2 从而要求每次执行都过人工审批——本 ADR
的建议是**不改**，永远留在 L1：探测的价值恰恰在于"低摩擦、可按需触发、可定时
触发"，如果每次探测都要人工投票通过，等同于取消这个功能；但这是产品负责人的
判断，不由实施方自行定夺。

### 四、Foundation-B 之前能上线什么（明确列举）

**现在就能上线、且今天就能跑通**：

- `assurance.probe.declare@1` / `.cancel@1` / `.run@1` 三个 L1 Action，权限、
  审计、Environment 校验全部走现有 Foundation-A 内核，无需等待任何东西；
- **fake 模式**下 `assurance.probe.run@1` 对着假连接器完整跑通声明 → 探测 →
  结论的全链路，不需要负责人做任何操作、不产生任何真实费用；
- 两个独立的 Kill Switch（下一节）。

**真实模式额外前提**（缺一不可，任何一项不满足都拒绝执行并给出具体原因，
不是笼统的"未接入"）：

1. `core.connector_config.mode == 'real'`（该平台已经切到真实连接器）；
2. `core.connector_config.probe_credential_ref` 已登记（探测专用 API Key 的
   `CredentialRef`，与 `credential_ref` 只读 admin 账号分离，ADR-014）；
3. 探测目标主机在该平台的 `target_allowlist` 内（ADR-004）；
4. **平台级 Kill Switch**：`core.connector_config.probe_enabled = true`（新增
   列，通过新 Action `assurance.probe.kill_switch.set@1` 单独授权，见规格
   文档——刻意不并进 `connector.config.set@1`，让"允许探测花钱"和"改连接器
   怎么连上游"是两个可以分别授权、分别审计的操作）；
5. **全局 Kill Switch**：环境变量 `XM_ASSURE_PROBE_ENABLED=true`，与
   `internal/platform/jobs/deployed_schedule.go` 里
   `XM_CONNECTOR_PROBE_ENABLED`/`XM_SUB2API_SYNC_ENABLED` 同一套先例——运维在
   拿不到数据库、只想"立刻全局停"时的最后一道闸（宪法 26 条）。

**继续留给 Foundation-B/XM-0030 的**：真正的幂等键基础设施、写后读取确认、
人工审批流、Step-up MFA、冷却期/取消窗口作为 Action 内核的一等特性——本 ADR
不重造一套并行的审批系统，只用 L1 已经允许的工具。

### 五、成本/预算铁律

- 每次探测**固定极小 Prompt**（声明时从平台预置的模板集合里选，不接受用户
  自由文本 Prompt——与原型"检测任务"表格里"模型指纹/基准题集/上下文长度/
  最小可用请求"这类固定任务名对应，杜绝把探测当成一个可被滥用的"自由调用
  出口"）；
- 每次探测 `max_tokens` 硬上限（声明时只能往小填，不能超过平台常量上限）；
- **每平台每日探测预算硬顶**（按探测次数计数，业务日边界重置），超出后新的
  `probe.run` 请求被拒绝并显式记一条"预算耗尽"的历史记录（宪法 12 条：
  拒绝执行也要可见，不能悄悄消失）；
- 同平台并发上限 1（同一时刻只允许一个探测批次在跑），同一声明连续两次
  "发起检测"之间有最短冷却间隔；
- 失败探测**不自动重试**——探测已经花过一次真钱，重试意味着可能再花一次，
  由 River 层面显式关闭自动重试（`MaxAttempts=1`），失败就是失败，记下来，
  等下一次正常调度或人工再次触发；
- 本片**不依赖** R2-15（`docs/superpowers/specs/2026-08-29-r2-15-connector-budget-design.md`）
  的 `SourceBudgetAuthority`/`PollState` 机制——那套四层预算系统本身除 R215-0
  设计文档外全部是 NO-GO（未获批准迁移/未接生产），探测预算是本片自建的、
  独立的、简单得多的计数器；R2-15 落地后可以评估把探测注册成它的 `cost_class`
  之一（现有 `contracts/connectors/budgets.v1.json` 里的 `probe` cost_class
  条目都是 1 行的 `GET /health`/`GET /api/status` 健康检查，与本片"真实模型
  推理调用"性质不同，不应混为一谈）。

### 六、结果的诚实规则

- 每条探测结果必须带明确的结构化结论（一致/退化/超时/形状异常等），不得用
  笼统的"通过/不通过"掩盖部分事实；
- 首字节延迟只在真实测量到时才填，测不到就是 `null`，与 ASSURE0 的
  `MeasuredTTFB` 纪律一致，不用总耗时冒充首字节；
- 探测结果**必须落在自己独立的表/命名空间**，绝不与 `ops.metric_observation`
  或 ASSURE0 的被动指标共用同一套 key——ASSURE0 交接文档的 follow_ups 已经
  明确警告过这一点："不能与本片的被动指标共用同一套 metric_key 命名空间，
  否则概览页会分不清一个数字是用户真实调用统计出来的，还是我们主动打的
  探测";
- 检测任务/历史记录（主动）与保障概览/历史记录（被动，ASSURE0）在同一个
  "渠道保障"页面上必须保持视觉和语义可分辨，不得合并成一张让人误判数据
  来源的表。

## 理由

探测通道隔离保证：真实模型调用这条全新的、有真实成本和副作用的出站通道，
拥有自己的凭据、自己的预算闸、自己的 Kill Switch 和自己的数据命名空间，
不与既有的只读 admin 通道（ADR-018）或业务写通道（ADR-004）混淆，也不需要
等待 Foundation-B 的审批基础设施就能以合适的风险等级安全上线。

## 边界与后果

- 探测凭据、探测目标主机的白名单校验、探测预算计数器的实现细节见配套规格
  文档 `docs/superpowers/specs/2026-09-03-xm-assure1-active-probes-design.md`；
- `core.connector_config` 需要新增 `probe_enabled`、`probe_credential_ref`
  两列（迁移随 XM-ASSURE1-core 落地，不在本设计片提交）；
- 本 ADR 不创建、不修改 `contracts/actions/*.json` 文件——项目文档治理要求
  "文档修改与代码同 PR"，`assurance.probe.*` 的 Action 契约文件应随
  XM-ASSURE1-core 的代码一起提交，而不是在这个纯文档设计片里提前落地一个
  尚无对应代码的"契约"（这与 `registry.connection.set_status.v1.json` 这类
  "先声明、代码已注册但风险等级挡执行"的既有先例不同——那些契约是跟着已注册
  的代码一起进仓库的）。本 ADR 与配套规格文档里的 JSON 结构是**设计稿**，
  不是冻结契约，字段名/结构在实现前仍可能被验收线要求调整。

## 替代方案

1. **全部划为 L2，等 Foundation-B 落地再开工**：否决——与"先 fake 模式验证"
   的既定路线冲突，XM-0030 尚未拍板，交付时间不可控。
2. **复用 ADR-018 的只读 admin 账号发探测**：否决——ADR-018 四道闸的对象是
   只读 admin/DB 通道，探测天然是"发一次真实推理请求"，塞进只读闸的形状会
   破坏"Connector 包内无写路径"（闸 4）的字面意义，也拿不到一个能发推理请求
   的 API Key。
3. **扩展现有 `connector_probe` 周期任务，让它顺便也打模型接口**：否决——
   `connector_probe` 刻意保持零成本、零凭据切换（只调 Version()/Health()），
   把真实计费的模型推理调用塞进同一个 worker 会让"健康探测"这个名字的成本
   含义变得不诚实，且违反 ASSURE0 follow_ups 对"被动/主动不共用命名空间"的
   明确要求。

## 重评条件

- XM-0030（Foundation-B Action Advanced Controls）拍板落地后，复核
  `assurance.probe.run@1` 是否需要提升风险等级或接入正式审批流（本 ADR 的
  建议是不需要，见"待拍板问题"）；
- R2-15 R215-1 及以后阶段获批、`SourceBudgetAuthority` 真正可用后，复核是否
  把探测预算迁移进 `ConnectorBudgetPolicyV1`，注册为独立于现有健康检查
  `probe` cost_class 的新类别。
