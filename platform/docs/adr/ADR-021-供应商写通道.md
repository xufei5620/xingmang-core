# ADR-021：供应商写通道

| 项 | 值 |
|---|---|
| 状态 | 待验收线批准（提出于 XM-CARD0） |
| 日期 | 2026-09-04 |
| 来源 | XM-CARD0/1/2（Infini 卡服务接入） |

## 背景

平台此前对外只有一条 HTTP 通道：`connector.ReadOnlyTransport`。它在
`RoundTrip` 层拒绝一切非 GET/HEAD 请求（ADR-018 闸 4，错误类型
`write_attempt`），也就是说**平台发不出任何 POST 给任何上游**。

接入 Infini 卡服务时这条闸挡住了全部业务：除查询外，开卡、充值、赎回、
冻结、解冻、查看卡面六个接口全是 POST。

## 决策

新增一条与只读通道**并列**的传输层 `connector.VendorWriteTransport`，
用于平台作为客户去调用的供应商 API。

两条通道的闸门一一对应：

| 只读通道（ADR-018） | 供应商写通道（本 ADR） |
|---|---|
| 方法白名单 GET/HEAD | 方法白名单 GET/HEAD/**POST** |
| 主机 allowlist 完全相等匹配（不做后缀匹配） | 同左 |
| allowlist 为空则拒绝一切（fail closed） | 同左 |
| 拒绝重定向 | 同左 |
| 强制超时 | 同左 |
| 包内无写路径（由类型强制） | **消灭不掉**，见「边界与后果」 |

## 理由

ADR-018 的适用范围是明确的：「平台对 NewAPI/Sub2API 建立独立只读账号」。
那两个上游的**业务真相不归平台所有**，平台去写它们等于越界——这正是宪法
条款 5「不直写第三方原始表」要防的事。

Infini 属于另一类：平台是它的**客户**，调用的是它公开发布的写接口。
这跟「写第三方的数据库」不是一回事，正如平台调用支付网关的下单接口
也不算越界。把这两类混在一条禁令下，结果是平台永远无法采购任何需要
API 交互的服务。

## 边界与后果

**「包内无写路径」这一条在写通道上消灭不掉。** 只读通道靠类型系统保证
包里不存在写操作；写通道的存在意义就是写，没有等价的机械保证。替代的
约束是上层纪律：

1. 所有经写通道的业务操作**必须**走 Action（宪法条款 2 / ADR-003），
   由内核强制审计与权限；
2. 花钱的操作必须有幂等键与金额上限，且上限未配齐时 fail closed；
3. 上游不提供幂等能力时（如 Infini），平台必须自建操作台账并显式表示
   「不确定是否已生效」的第三态，禁止自动重试。

**这条通道是新增的攻击面。** 平台从此具备向外部发 POST 的能力。缓解措施
是 allowlist 与方法白名单，以及每个使用者必须在连接配置里显式登记目标主机
——写通道不接受通配。

**适用范围仅限「平台作为客户购买服务的供应商」。** 复用本 ADR 去写
NewAPI/Sub2API 或任何「平台不拥有其业务真相」的上游，仍然违反 ADR-018 与
宪法条款 5。

## 替代方案

**放宽 ReadOnlyTransport 允许 POST**：否决。那会让现有九个只读连接器
一并获得写能力，把 ADR-018 的机械保证降级成代码评审。

**在 `connectors/infini` 包内自建 transport 绕开平台层**：否决。绕开平台
统一闸门等于把 allowlist、重定向拒绝、超时这三件事交给每个连接器各写一遍，
迟早有人漏写其中一样。

## 重评条件

- Action Advanced Controls（Foundation-B / XM-0030）落地后：届时写通道上的
  操作可以真正获得审批、Step-up MFA、冷却与 Kill Switch，本 ADR 的
  「上层纪律」清单应当据此收紧。
- 出现第二个供应商写接入时：复核 allowlist 与方法白名单是否仍然够窄。
