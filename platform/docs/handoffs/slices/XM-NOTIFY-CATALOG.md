# XM-NOTIFY-CATALOG：企业微信消息目录（收到每条消息代表什么）

- **status:** implemented，未上线。**一份文档 + 一个把它钉住的测试**，不改任何
  运行时代码。
- **branch:** `ai/claude/XM-NOTIFY-CATALOG`，**由两条分支合并而来**：
  `ai/claude/XM-NOTIFY-ENVELOPE`（信封）+ `ai/claude/XM-UPSTREAM-VERSION-ALERT`
  （R6 规则）。合入验收线时这两条要先进去，或者直接合本分支（它已包含两者）。
- **产品负责人 2026-09-06 原话：**「需要对通知建立规范，做好分类，通知模板，
  **让我们清楚在企业微信那边收到每条消息代表什么**。」

## 前一片做了什么，这一片补什么

`XM-NOTIFY-ENVELOPE` 交付了统一信封与 `docs/modules/notify/README.md`。那份文档
回答的是"信封为什么长这样"——**它是写给改代码的人的**。产品负责人那句话的
后半句还没有被回答：群里弹出一条消息，**它是什么、要不要现在动手、去哪处理**。

这一片补的就是那半句：`docs/modules/notify/CATALOG.md`。

## 目录里有什么

四个域、十二种消息，每一种都有：触发者、严重度、**真实渲染出来的示例**、
以及"你该做什么"。

- **告警**（7 条规则）：一张表，逐条给出规则键、什么情况下响、什么时候自己好、
  你该做什么。
- **卡片**（3 种）：验证码/待验证、交易、状态变更。
- **接码**（1 种）：收到验证码。
- **开票**（1 种）：用户提交申请。

外加四件收件人最需要先知道的事，和一份「收不到消息时按这个顺序查」。

## 三个在写的过程中查出来的事实

**一、告警的恢复永远不推。** `ListAlertsPendingNotify` 只取
`status IN ('OPEN','REOPENED')`。运营只会收到"出事了"，不会收到"好了"。
这不是 bug（重复推送的成本很实在），但**它必须被说出来**——不说的话，
一个人会以为没收到恢复通知就是还没恢复。

**二、持续期间不重推，静默到期会重推，复发会重推。** 三种转换三种行为，
每一种都有它的理由（写进目录了）。这些语义只存在于 SQL 与 store 的分支里，
运营无从知道。

**三、示例必须是渲染出来的，不能手写。** 目录里每一段消息都是把真实渲染函数
跑一遍抄进来的（告警、卡片三种、接码来自平台仓库；开票那条来自开票仓库的
`notify.EnvelopeFor`）。手写会抄错，而这份文档存在的全部意义就是"对得上"。

## 测试：目录的完整性由测试保证，不由自觉保证

`internal/platform/notify/catalog_test.go` 四条：

1. `alerts.Rules(...)` 里的**每一个规则键**都必须出现在目录里。
   新增一条规则而不写目录 → 红。
2. 卡片三种 kind、接码与开票各自的 kind 都必须出现。
3. 四个域的徽标（`【星芒·告警】` 等）都必须出现。
4. **目录里的示例必须与真实渲染逐字一致**（告警一条、卡片交易一条）。

**做过变异验证**：把 `upstream.version.changed` 从目录里去掉（两处都去），
第 1 条如期变红并指名规则；把示例里的「累计 4 次」改成「累计 5 次」，
第 4 条如期变红并打出实际渲染结果。

本轮已经三次遇到「注释说没做，其实早做了」（凭据页探测两格、兼容矩阵、
工作台失败任务）。**一份写完就开始过期的目录满足不了负责人那句话**，
所以完整性必须是测出来的。

## 门禁

`gofmt` 干净、`go test -p 1 -count=1 ./...` 全绿、
`scripts/check-governance.sh` 退出 0、`gitleaks protect --staged` 无泄漏。

**gitleaks 踩坑（第二次）**：测试里那个点分的指标键字面量（sub2api 的日收入
那条）被 `generic-api-key` 判成泄漏。仓库禁止 allowlist（会把真泄漏一起静音），
按既有做法抽成常量解决。

**这一段本身也踩了同一个坑**：最初这里原样写出了那个字面量，于是这份交接文档
自己被扫出一条 finding。写"某某键"而不是把它抄一遍，是同一条纪律的延伸——
**连描述误报都不该复现触发它的字符串**。

## follow_ups（都要产品负责人拍板，不是技术卡点）

- **要不要加告警恢复通知。** 加了群消息量翻倍。
- **开票除「提交」外要不要推审核通过 / 开具完成。** 每多一种就多一份群消息，
  太吵会让人把整个群静音，那比不发还糟。
- **带序号的告警号**（`AL-2609-0007`）。今天编号是规则键，同一规则多条告警
  编号相同。要流水号得后端加字段——前端生成会让两个人看到不同的号。
- 开票发件箱**只能查库**，管理端没有只读视图。收不到通知时排查第 3 步在开票
  这条线上走不通。
