## 规范里最要紧的三件事

**一、第 0 步先问"该不该是一条群消息"。** 三个问题：有人收到之后会做什么吗
（答不上来就别发）；它会不会自己重复（会 → 那是告警规则，不要自己发消息）；
它一天响几次（没数就先去数）。群消息是所有人的注意力，加一条容易、减一条要
等到有人受不了。

**二、两种模型选错了后面全是补丁。** 「这件事有『还在不在』这个问题吗」——
有就是告警模型（收敛/去重/恢复/静默都是现成的），没有就是事件模型（推荐配
发件箱：入队与业务写入同事务，投递带重试）。把事件套进告警模型会得到一条永远
不解除的告警，把告警列表变成流水账。

**三、噪声预算，配一个真实例子。** 产品负责人截图里同时躺着三条：

```
[CRITICAL] 指标 newapi.channels.status 同步失败 … 错误码 unavailable
[CRITICAL] 指标 newapi.models.usage   同步失败 … 错误码 unavailable
[CRITICAL] 指标 newapi.payments.daily 同步失败 … 错误码 unavailable
```

同环境、同规则、同来源、同错误码、同一秒——根因只有一个（`newapi-prod` 那一刻
不可达），收件人要读三遍才确认这是一件事。**这不是 bug**：R1 的去重键按指标去重
本身是对的（三个指标确实各自失败、也各自恢复）。问题在于**去重键决定"算不算
同一条告警"，但没人决定"要不要合成同一条消息"**。规范因此要求每个新接入的功能
先回答：一个根因会同时触发几条、能不能按根因合并、静默期多长。

## 模板：写成数据，由测试守住

散文写的模板会和实现漂开。所以每种消息的**必备行**声明在
`internal/platform/notify` 的 `templates` 里：

| 编号 | 必备行 |
|---|---|
| `XM-ALERT-<规则键>` | 规则、状态、首次发现、最近发现 |
| `XM-CARD-transaction` | 商户、金额、状态 |
| `XM-CARD-status_change` | 当前状态 |
| `XM-SMS-code` | 号码、验证码、供应商、时间 |
| `XM-INVOICE-request.submitted` | （在开票仓库渲染，文档登记，校验在那边） |

三处设计取舍：

- **告警整个域共用一套必备行**（`TemplateFor` 先精确匹配 `XM-域-Kind`、再回退
  到 `XM-域`）。每加一条规则都登记一遍既没必要也会漏，而"什么规则、现在什么
  状态、响了多久"是每条告警都要回答的。
- **只声明必备行。** 可选行钉死会逼出一堆空值占位，而空值行本来就该被省略。
- **模板缺行不挡投递。** `MissingTemplateLines` 只给测试用，不在渲染路径上：
  半条消息胜过没有消息，缺字段该在测试里被拦下、不该在运行时把通知丢掉。

## 测试

`internal/platform/notify/template_test.go` 五条，**拿各域真正的渲染函数跑一遍**
再逐行核对（不是核对散文）：告警、卡片交易、卡片状态变更、接码各自的必备行；
`MissingTemplateLines` 要**点名**缺了哪几行，且**空值算没给**；未登记的域返回
空模板而不是报错（模板是"已登记的必须守"，不是"没登记的不许发"）。

另有一条防恒真：告警那条断言完之后再确认"告警域确实有模板"——模板为空时那个
循环什么都没测。

**做过变异验证**：把卡片交易的「金额」那一行删掉，`TestCardMessagesCarryTheir
TemplateLines` 如期变红并点名「金额」。

门禁：`go test -p 1 -count=1 ./...` 全绿、`gofmt` 干净、
`scripts/check-governance.sh` 退出 0、`gitleaks protect --staged` 无泄漏。

## 顺带确认的一件事

**生产现在跑的是旧格式**（发布线的 `alerts.FormatWeComMarkdown` 逐字对得上
截图）：没有域徽标、没有编号、没有"该去哪处理"。信封那一片
（XM-NOTIFY-ENVELOPE）还在分支上没合入。截图里那三条一旦发版就会变成带
`【星芒·告警】` 徽标与编号的形态。

## follow_ups

- **跨条目合并**（上面那个三条同根因的例子）没有做，是本文点名的第一个缺口。
  它要在投递层做：同一轮评估里 `(规则, 环境, 来源)` 相同的多条合成一条，正文
  列出受影响的对象。属另一片，且会改变运营看到的消息形态，值得先拍板。
- 没有分级路由（critical 进这个群、info 进那个群）。今天所有域进不进同一个群，
  只取决于运营把地址填成一样还是不一样。
- 开票那条的模板校验在开票仓库，平台这边只登记。两边漂开时没有机制会说话——
  跨仓库的契约核对是已知的老问题（[[cross-repo-contract-verify]]）。
