# 接入通知：新功能要发企业微信消息时，照这份做

> 另外两份：`README.md`（信封为什么长这样，写给改 notify 包的人）、
> `CATALOG.md`（收到每条消息代表什么，写给运营）。
> **这一份写给"我在做功能 X，它需要发通知"的人。**

产品负责人 2026-09-06：「其实本身就有已经在发送通知的话，我需要的是建立好规范，
因为可能不同的功能都需要接入这个通知。」

---

## 第 0 步：先问它该不该是一条群消息

**这一步不是客套。** 群消息是所有人的注意力，加一条容易，减一条要等到有人
受不了。三个问题按顺序问：

1. **有人收到之后会做什么吗？** 答不上来就不要发。"留个记录"用审计事件，
   "以后要查"用管理端的列表页——两者都不该占用群里的一行。
2. **它会不会自己重复？** 一个持续存在的状况（同步失败、余额不足、版本变了）
   属于**告警模型**，不要自己发消息：加一条告警规则，收敛、去重、恢复、
   静默这些全都是现成的（见下面「两种模型」）。
3. **它一天会响几次？** 心里没数就先去数。一条一天响两百次的通知，等于把
   整个群变成噪声，代价由所有人承担，而不只是你这个功能。

---

## 两种模型：选错了后面全是补丁

### 告警模型（`alerts`）——描述一个**持续存在**的状况

条件成立就开一条、持续命中只累加计数、条件不再成立自动恢复、可以被确认与
静默。**判据：这件事有"还在不在"这个问题吗？** 有，就是告警。

接法：往 `internal/platform/alerts/rules.go` 加一条规则。要定的四件事：
`Key`（进消息的「规则」行，也是编号）、`Condition`、`Severity`、
`DedupKey`（**决定什么算"同一条"**）、`Recovery`（什么时候自动好）。
规则数在 `rules_test.go` 与 `consistency_test.go` 各有一个计数断言，
**故意**要求每加一条规则都改一次测试——那是让你停下来想想去重键的地方。

### 事件模型（`cards` / `sms` / `invoice`）——描述一件**发生过就完了**的事

一笔消费、一个验证码、一次提交。没有"仍然满足条件"这回事，也就没有恢复。

**不要把事件套进告警模型**：套进去会得到一条永远不解除的告警，把告警列表
变成流水账（这条取舍在 `cards/notify.go` 的注释里写过一次）。

接法：在自己的包里构造 `notify.Envelope` 并渲染，投递走自己的通道。
**推荐用发件箱**（开票那条的做法）：入队与业务写入同事务，投递由后台循环
带重试完成，成败留痕。直接在请求路径里发 HTTP 会让用户等你的群机器人。

---

## 第 1 步：选域，或者新增一个域

今天四个：`alert` / `card` / `sms` / `invoice`（`notify.Domain`）。
域决定徽标（`【星芒·告警】`）与编号前缀（`XM-ALERT-…`）。

**先看能不能挂进已有的域。** 新增一个域意味着群里多一种徽标，运营要多认一个。
只有当它有**自己的凭据、自己的收件人**时才值得新增——比如卡片 3DS 的码只想
给自己看，接码的码给另一批人。

新增一个域要做的事（缺一不可）：

1. `notify.Domain` 加常量，`domainLabels` 加中文标签。
2. 决定凭据引用（`secret://<域>/…-webhook`），登记进 `CATALOG.md` 的通道表。
3. `CATALOG.md` 加一节，说明这个域的消息种类与"你该做什么"。
   **`catalog_test.go` 会检查域徽标在不在目录里，不写就红。**

---

## 第 2 步：定严重度

**按"要不要立刻动手"分，不按"这件事重不重要"分。** 收入统计当然重要，
但它晚十分钟没人需要跳起来。

| 取值 | 什么时候用 | 收件人的反应 |
|---|---|---|
| `critical` | 已经在丢数据 / 已经不可用 | 放下手里的事 |
| `warning` | 有时效或会恶化（验证码、余额、卡被锁） | 今天之内处理 |
| `info` | 周知、记录用 | 看一眼 |

两条坑：

- **企微没有独立的红与橙**，`critical` 与 `warning` 只能同色。**区分靠中文词**
  （严重 / 警告 / 通知），不要指望颜色。
- **不要把所有东西都标成 `critical`。** 全是严重等于没有严重。

## 第 3 步：写正文

```go
notify.RenderWeComMarkdown(notify.Envelope{
    Domain: notify.DomainCard, Kind: "transaction",
    Severity: notify.SeverityWarning, Environment: env,
    Title: "卡片消费 acct-01 · **** 4321",
    Lines: []notify.Line{
        {Label: "商户", Value: merchant},
        {Label: "金额", Value: amount},
        {Label: "原因", Value: failureReason},
    },
    Action: "管理后台 → 卡片管理",
})
```

- `Kind` 是**域内稳定的事件键**，进编号（`XM-CARD-transaction`）。它标识
  一类事件，不是一条实例——**定了就别改**，群里搜它能捞出同类的全部历史。
- `Title` 一句话说清"什么东西出了什么事"，把最要紧的值放前面
  （验证码就放码本身：正在付款的人要一眼抓到）。
- `Lines` 是"标签：值"。**空值行会被自动省略**，不必自己判断。
  值来自 map 时用 `notify.SortedLines` —— map 迭代顺序随机，同一事件两次渲染
  出的消息不一样，会让"这条我是不是收到过"无法判断。
- `Action` 是"该去哪处理"，我方闭集文案。**纯周知才留空。**

### 每种消息的模板（必备行）

**模板不是散文，是代码里的一张表**（`internal/platform/notify` 的 `templates`），
由测试拿**真实渲染结果**逐行核对。漏一行、改一个标签，测试就红——而不是等运营
在群里看见一条缺关键字段的消息。

| 编号 | 必备行（按此顺序） | 可选行 |
|---|---|---|
| `XM-ALERT-<规则键>` | 规则、状态、首次发现、最近发现 | 指标、详情 |
| `XM-CARD-challenge` | （无必备行，码在标题里） | 有效期、说明 |
| `XM-CARD-transaction` | 商户、金额、状态 | 原因 |
| `XM-CARD-status_change` | 当前状态 | — |
| `XM-SMS-code` | 号码、验证码、供应商、时间 | — |
| `XM-INVOICE-request.submitted` | 申请单号、金额、来源、状态、提交时间 | — |

几条读法：

- **告警整个域共用一套必备行**，不按规则键分。规则每加一条都登记一遍既没必要
  也会漏；而"什么规则、现在什么状态、响了多久"是每条告警都要回答的。
- **只声明必备行。** 可选行由各域自己判断——把可选行也钉死会逼出一堆空值占位，
  而空值行本来就该被省略（`RenderWeComMarkdown` 会自动省）。
- **开票那条在开票仓库里渲染**（ADR-018 通道隔离），平台侧的表登记它是为了让
  这张表是完整的，校验由开票侧自己的测试做。
- 新增一种消息时**在 `templates` 里加一行**，然后让你的测试调
  `Envelope.MissingTemplateLines()` ——它返回模板要求但你没给的行，
  空值也算没给（一行「金额：」比没有这一行更糟）。

**模板缺行不会挡住投递。** `MissingTemplateLines` 只给测试用，不在渲染路径上：
一条缺字段的消息也要发得出去——半条消息胜过没有消息，而缺字段该在测试里被
拦下，不该在运行时把通知丢掉。

## 第 4 步：这些东西永远不许进消息

群消息留在聊天记录里，**那不是我们能控制的存储**。所以：

| 绝不出现 | 该用什么替代 |
|---|---|
| 完整卡号 | 掩码（`**** 4321`） |
| 完整手机号 | 掩码 |
| 开票抬头 / 税号 / 银行账号 / 地址 / 电话 | **一个都不放**——它们在库里是加密的，通知只读非 PII 字段 |
| 任何凭据、Webhook 地址、Token | 什么都不放；连投递失败的错误里都不许有 |
| 上游返回的自由文本（`errmsg` 之类） | 只转述我方分类过的短码 |

**排版上还有一条硬规矩：只有闭集能用 markdown 语法。** 徽标、严重度、环境、
编号、处理入口是我方文案，上色安全；**标题与每一行的值由上游决定**，可能带
`*`、`#`、反引号，一律进 `> ` 引用块且不带任何标记——带标记就要转义，漏转义
的后果是排版错乱甚至整条发不出去。`RenderWeComMarkdown` 已经替你做了，
**不要绕过它自己拼字符串**。

---

## 第 5 步：凭据

整个 Webhook 地址就是凭据（企微把鉴权 key 放在查询参数里）。两条路，看你在哪：

- **平台侧**：走 CredentialRef（`secret://<域>/…-webhook`），运营在
  管理后台 → 设置 → 凭据管理里填。
- **开票侧**（跨 ADR-018 通道边界的系统）：存自己的库、在自己的管理端设置页填
  （XM-INV-NOTICE-WEBHOOK-SETTING）。

两条路共同的三件事：

1. **不要放环境变量或宿主机文件。** 运营会调的东西不该长在服务器上——换群、
   改错、轮换都要 SSH 上去再重启，这已经被推翻过一次。
2. **投递时现取，不要构造时定死。** 换了地址下一条消息就该用新的。
3. **形状校验放在保存那一刻**，不是进程启动时。人就在页面前。

## 第 6 步：噪声预算——这条最容易被跳过

**先看一个真实的例子**（2026-09-06 生产，产品负责人截图）：

```
[CRITICAL] 指标 newapi.channels.status 同步失败 … 错误码 unavailable
[CRITICAL] 指标 newapi.models.usage   同步失败 … 错误码 unavailable
[CRITICAL] 指标 newapi.payments.daily 同步失败 … 错误码 unavailable
```

三条消息，**同一个环境、同一条规则、同一个来源、同一个错误码、同一秒**。
根因只有一个：`newapi-prod` 那一刻不可达。收件人要读三遍才确认这是一件事。

这不是 bug——R1 的去重键是 `metric.sync.failed:<环境>:<指标键>`，**按指标去重
本身是对的**（三个指标确实各自失败了，恢复也是各自恢复）。问题出在**投递**：
去重键决定"算不算同一条告警"，但没人决定"要不要合成同一条消息"。

所以，加任何新通知之前，先回答：

1. **同一个根因会同时触发几条？** 一个上游挂掉会连带几个指标？一次批量操作
   会产生几个事件？答案大于 3 就要想合并。
2. **能不能按根因合并成一条消息？** 例如同一轮评估里、同一个 `(规则, 环境,
   来源)` 的多条告警合成一条，正文列出受影响的对象。
3. **静默期多长？** 事件模型没有"持续期间不重推"这层保护，一个循环里连发
   五十条的功能，第一天就会让人把群静音。

**目前还没有跨条目的合并机制**，这是已知缺口（见文末）。在它做出来之前，
新接入的功能自己负责不刷屏：能合的自己合，能攒的自己攒。

## 第 7 步：接入清单（照抄，逐条勾）

- [ ] 第 0 步三个问题都答过了，确实该发群消息
- [ ] 选对模型：持续状况 → 告警规则；一次性事件 → 事件模型 + 发件箱
- [ ] 选好域；新增域的话，`Domain` 常量 + `domainLabels` + 凭据 + 目录一节
- [ ] `Kind` 定了就不改（它进编号）
- [ ] 严重度按"要不要立刻动手"选，不是按"重不重要"
- [ ] 走 `notify.RenderWeComMarkdown`，没有自己拼字符串
- [ ] **模板登记进 `templates`**，并用 `MissingTemplateLines()` 在测试里核对
- [ ] 第 4 步那张表逐行核对过：掩码、无 PII、无凭据、不转述上游原文
- [ ] 凭据在后台配、投递时现取、保存时校验
- [ ] 噪声预算算过：一个根因最多几条、要不要合并、静默期多长
- [ ] **写进 `CATALOG.md`**：触发条件、严重度、**真实渲染出来的示例**、
      收到之后该做什么
- [ ] 测试：渲染逐字段、**载荷里没有 PII**（用反射钉住字段集合最稳）、
      未知取值原样显示、按字节截断、投递失败的错误里没有地址

**最后一条是硬门禁**：`internal/platform/notify/catalog_test.go` 会检查
每个告警规则键、每种事件 `Kind`、每个域徽标在不在 `CATALOG.md` 里，
**漏写就红**。示例也必须与真实渲染逐字一致——手写会抄错，而那份目录存在的
全部意义就是"对得上"。

## 已知缺口（不是让你绕过，是让你知道边界在哪）

- **没有跨条目合并**：同根因的多条告警各发一条（上面那个例子）。合并要在
  投递层做，属另一片。
- **没有恢复通知**：告警只推"开始"不推"结束"，要不要加是产品决策。
- **没有静默期配置**：事件模型的节流由各功能自己实现。
- **没有分级路由**：所有域的消息进同一个群还是分开，只取决于运营把地址填成
  一样还是不一样。没有"critical 进这个群、info 进那个群"这种能力。
