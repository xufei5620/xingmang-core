---

## 一、先看这两件事

**1. 权限那一片解除了一个当前生效的限制。**

生产上 `source_credit_events` 的 DELETE 是 2026-09-06 19:46Z **手工补**的。
RC102 的 roll-forward 新增了 `[0b/6]` 授权重放，会在每次部署时忠实执行策略文件
——而策略文件当时还收着这个权限。**本片上线之前，任何一次 roll-forward 都会
再次收掉它**，投影随即在某个账号上判死、readyz 转 503（RC102 那晚就是这么发生的，
持续约一个半小时，用户侧全程 200）。

**本次 roll-forward 会先应用新的策略文件，所以这个循环在本版终结。**

**2. 账本那一片会让「起点后充值」的数字变大，这是修好了不是坏了。**

以生产数据实跑的新旧对照：`1147` 从 0 笔变成 2 笔 ¥11；`1113`/`48`/`72` 从 0 笔
变成 1 笔（金额均为 ¥0，只影响笔数）；其余四个账号完全不变。

更要紧的是**未来**：改之前每个账号都带着一段自己的「盲区」——从策略起点到系统
为它建立余额基线之间，现有八个账号的盲区从 0 到 139 小时不等，落在盲区里的充值
一律不计入那一列。**新用户注册后立刻充值正好落在盲区里**，公告发出后这会是高发
场景。改后盲区概念消失。

## 四、上线后盯什么（本版与往常不同）

公告即将发出，人群会从 8 个账号变成潜在数百个。**盯守重点从「部署本身」转向
「新账号绑定时的追赶重放」**：

1. **就绪探针**。XM-INV-CATCHUP-BURST-BACKPRESSURE 记录过：**单个**账号解除
   追赶限制、重放三天积压，就造成 17 分钟 503。切块修复（`ELIGIBILITY_EVIDENCE_
   BATCH_LIMIT=25`）已于 RC99 生效，但只在 8 个账号上验证过，而现在积压是 12 天。
2. **待认领事件**。库里堆着 54.2 万条（用量 43 万、余额 10.9 万），来自全部
   2837 个上游注册用户。绑定一个活跃账号 = 把他那一份从搁置转为处理。
3. **投影任务队列**是否积压、有无新的 `dead`。
4. **新绑定账号的「起点后充值」是否非零**——这一版就是为它改的。

建议产品负责人**分批放量**（先 5–10 个用量大的用户，盯 30 分钟；再 50 个；
再全量），而不是一次性公告给全部人。这条已当面提出，负责人选择先发公告。
